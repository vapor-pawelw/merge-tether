# Automation and permissions

MergeTether is a local MR command center. Manual GitLab management works without a coding agent. All agent automation requires a compatible, signed-in Codex CLI or Claude CLI; the desktop applications are optional. Tasks run headlessly, with their progress, results and failures available in the main window. Up to four different MR workers run concurrently, with a single worker per MR. Persistent login and quota banners pause unstarted work for the affected provider. Login opens in the default terminal; explicit retry releases queued work, while stopped runs require their own deliberate retry.

Worker output is written to private files throughout execution. Validated complete results receive an account/run/head-bound completion checkpoint authenticated with a Keychain-held signing key and stored outside the worker directory, recoverable at startup. Ordinary Quit cancels worker process trees and waits for cleanup and persistence. Incomplete work remains Interrupted with retained files; raw partial output never establishes success or authorizes a remote write. CLI session persistence is disabled. Retry starts a fresh task, inspects the previous run and re-fetches current GitLab commits, discussions and drafts before continuing; existing work must not be duplicated. Force Quit bypasses that shutdown sequence.

## How a merge request moves through MergeTether

**When you are the reviewer**

1. A review request arrives. Draft MRs are tracked in Reviewing; their automatic work waits by default, while normal manual actions remain available. The selected CLI reviews ready MRs and saves warranted findings as private GitLab drafts.
2. Drafts wait on the relevant MR card. Open **Review and confirm** to read the complete discussion and private drafts, then publish the reviewed set or edit it in GitLab. Publication can also run automatically under the selected profile and publication mode.
3. New commits or author replies trigger a new re-review task. The first poll establishes a baseline; later events are deduplicated across restarts.
4. With **Resolve my verified findings during re-review** enabled, the agent checks each concern against the current remote head and resolves only threads whose first non-system note belongs to you. Unaddressed or uncertain concerns stay open with private draft replies. Turning the option off leaves resolution to you.
5. Automatic approval requires a current no-objections verdict, no pending drafts and every discussion resolved, in addition to your automation scope and CLI readiness.

**When you are the author**

1. Review feedback arrives. The agent handles existing incoming reviewer comments and verifies the relevant fixes and replies; it does not perform a fresh general review of your own MR or create merge requests. The comment verifier can privately escalate a specific technical question to this same stronger reviewer/fixer, including a potentially important defect incidentally noticed in the relevant code path. The agent independently confirms or disproves that hypothesis before making a warranted correction. It implements warranted fixes in an isolated worktree, tests, commits and pushes when follow-up push is enabled. It is instructed to keep work inside its run directory and leave other checkouts alone; this is a workflow rule, not a filesystem sandbox.
2. Before saving completion replies, the worker re-fetches the MR HEAD and verifies the remote source/test content. With push off, pending or failed, the proposal stays in the task result and no completion drafts are created.
3. Verified replies wait on the relevant MR card or qualify for the selected publication rule. MergeTether requests another review only when feedback is ready and unpublished replies no longer block it.
4. Failed pipelines and conflicts can become separate tasks. Trusted and Max check existing reservations and atomically claim unowned pipeline failures. Safe keeps external CI actions manual; pipeline ownership remains independently adjustable.
5. Automatic merge is enabled by Max and disabled by the other profiles. It checks ownership, scope, approvals, discussions, pipeline, the source commit, dependencies and the stack target.

Reviewing cards show the MR author by display name (hover for the account handle), the review-request source when known, and participation in your review threads. Historical replies in resolved threads do not count as pending work. Each card explains the next step and offers an action where needed; queued reviews and verification show automatic progress, while waits on other reviewers remain neutral. Without a recorded request source they say **Tracked for review**; missing discussion data is shown honestly rather than implying a first review. Proposals show the MR author and originating event.

When a current-head review verdict no longer covers the discussion text, the workflow can recheck it once for that evidence context, including after a restart. This uses the existing review-update rule and respects its execution mode and scope. Known published private drafts do not invalidate their own review, and resolution-only updates do not trigger another attempt. Once a fresh review covers the discussions, later text changes can start a new attempt even if they restore an earlier comment body. Automatic approval still requires the current verdict and all existing discussion and policy checks.

**Review and confirm** places private drafts with checkboxes and expanded original threads directly under the publication controls. All drafts present when Details opens are selected by default; closing discards the selection, and reopening selects the current set again. New or edited drafts are not silently selected during an open session. The MR card’s separate **Publish all and continue** action ignores this window-local selection, but publishes only the exact displayed draft IDs individually. New drafts arriving after its check are excluded. Manual publication waits while an agent is preparing drafts, and checks the current account, source and discussion context before sending. Other discussion history remains below without duplicating pending drafts. An **AI** badge indicates a verified agent identity or a high-confidence assessment bound to the current note and its content. **Human** and **AI uncertain** are separate assessed outcomes. No badge does not prove manual authorship; the badge does not authorize publication or resolution.

Each private draft has a **Delete draft** action with confirmation. Deletion applies only to the exact displayed draft after fresh account, MR and draft checks; an edited draft must be reviewed again. Other drafts are preserved. Deleting a draft never approves the MR, resolves a discussion or changes the recorded review verdict.

Once comments have been presented for review, MergeTether remembers a **Finish comment review** checkpoint for that account and MR, including across restarts. Deleting or publishing drafts in GitLab does not finish it: the user could still be composing another comment. After the drafts are handled, **Finish comment review** appears directly on the MR card on macOS and iOS, as well as in Details. It checks the displayed commit, MR context, discussion content, current account and a fresh empty draft list. New drafts or changed evidence keep the checkpoint pending. Details explain which subsequent approval, re-review or merge checks it blocks. Read-only assessments and independent feedback, commit and pipeline work can continue.

**Publish all and continue**, or publishing the complete selected set, can finish comment review after successful publication, an unchanged reviewed context (allowing only the new own comments just sent), and a fresh check that no drafts remain. Partial or uncertain results keep the checkpoint. Successful automatic publication can finish it under the same checks without an extra click. Completing comment review enables the existing readiness checks; it does not override missing approvals, unresolved discussions or review concerns. Older paired phones can still read the board without receiving action types they do not support; the new direct comment controls require the updated iOS app.

Automatic completion also requires proof that the automatic workflow published every draft observed during this checkpoint. If a user deletes or handles any of them elsewhere, automatic publication of the remaining drafts keeps **Finish comment review** pending. This evidence survives a restart; a read started before completion cannot reopen the completed checkpoint.

An MR has local task history. A process reporting success does not prove that a fix reached GitLab, a review remains current or a pipeline passed. A follow-up worker finishes its part after the required fix, verification and sealed private replies; publication and reviewer acceptance are subsequent steps. Historical blocked workers with complete sealed reply records can enter independent current-source verification without rewriting their execution history. A later sealed blocked result at the same source revision does not strand other owned replies. Missing seals, failed or active work and mismatched source evidence retain their existing fences. A raw worker seal is only an origin candidate; app-known run/account context, fresh source, discussion and claim checks and the configured publication policy still apply.

Pending drafts do not prevent a read-only check of existing feedback or configured follow-up work for independent incoming comments. A private reply prevents duplicate follow-up in its own discussion; unrelated and user-created drafts remain unchanged. Enabling automation for a paused Draft MR, disabling the global Draft pause, or enabling a repository default while that pause is off first asks for confirmation explaining the work and permissions involved. Cancelling keeps the previous policy. Draft MRs default to tracking-only; an effective Always on choice or a disabled global Draft pause enables their configured work. Any pending private reply still prevents automatic discussion resolution and re-review requests. A historical unbound follow-up can close once its own current requirements are addressed and required replies are published, even while unrelated drafts or feedback remain. The assessment itself never fixes code, pushes or publishes replies.

If an existing app-created reply makes an unsupported claim, configured feedback automation returns that exact reply to the selected coding agent. It can correct its wording or implement and verify a justified fix under the existing push permissions. It does not start a new review of your own MR. Repairs retain their original discussion and draft identity; user-created or changed drafts are excluded. An independent current-content check and the publication policy still decide whether the corrected reply may be published. Automatic repair attempts are bounded and recorded across restarts.

A reply that still needs a decision is identified as a **Prepared reply**, with its exact text and a link to the source discussion in Details. Technical verification evidence stays collapsed. A rejected statement is distinct from a failed attempt to fetch current evidence.

Incoming mentions without a known action may receive a read-only semantic assessment using the selected lightweight model. Only a proven informational event is acknowledged automatically, after a fresh account, MR and discussion check. Ambiguous or actionable notices stay available to read. Handled-event banners follow the existing optional banner preference.

## CLI setup and execution

Choose the provider in **Settings → Automation → Coding agent**. Setup verifies the executable, supported headless options and sign-in before accepting a selection. A missing or incompatible CLI can be installed through the provider’s official installer; sign-in opens Terminal. Cancelling or failing setup keeps the previous selection.

The CLI requirement applies even when automatic re-review verification is off. Desktop installation does not establish CLI readiness. Dependency checks run independently of GitLab polling, and missing CLI/sign-in is shown in the main app. Manual publication and other explicit GitLab actions remain available.

Codex reviews, feedback fixes, pipeline fixes, conflict work and reply corrections use the configured coding model and reasoning setting. Claude full tasks use the model configured in Claude CLI. The lightweight re-review readiness assessment has its own model setting.

The optional starting folder applies to manually opened CLI sessions. Desktop destinations receive the MR prompt without a starting folder. Automated workers start in separate per-run directories and are instructed to keep clones and worktrees there. They have full read, write, command and network access, without a CLI filesystem sandbox or interactive approval prompts. The additional project-task setting controls which configured tasks may run; it does not grant or restrict the worker’s tools.

Full tool access does not change the task’s GitLab authorization. Publication, approval, merge, thread resolution, author-follow-up push and conflict push keep their separate instructions and live app/helper checks. Executable work retains concrete failure diagnostics. Purely read-only assessment failures receive bounded automatic retries (three attempts with two- and eight-second backoff); after exhaustion, a fifteen-minute cooldown prevents repeated polling from restarting the budget immediately. Author-feedback assessment owns that budget end to end: each attempt makes at most one provider call, including through the app’s shared verifier wiring. The cooldown remains bound to the same account, configuration, MR evidence and reviewer-participation preferences; ordinary refreshes do not reopen it. Standalone re-review verification retains its separate two-attempt provider limit. A later poll can recover without requiring a manual MR action. Remote actions and semantic verdicts are not replayed by these retries. The separate lightweight re-review verifier has full CLI tool access with a read-only task: it can fetch live MR evidence through `glab`, but does not publish, resolve, push or merge. The app performs those actions under their configured policies.

These task permissions are not an operating-system or credential sandbox. Workers retain the signed-in account's tools and credentials, so app-side checks do not technically mediate arbitrary direct commands issued by a worker. Authenticated evidence detects substituted app records; it does not prove the semantic correctness of a review or defend against arbitrary same-user execution.

Provider configuration is currently explicit but different. Codex tasks ignore user `config.toml` and execution-policy `.rules` files and disable the app/plugin/memory integrations named in their invocation. `--ignore-rules` is not a promise that Markdown instructions or manually loaded skills are ignored. Claude coding tasks retain their normal settings sources, while supplying app settings and an empty strict MCP configuration; read-only verifiers explicitly suppress settings sources. Applicable skills remain part of the instructed workflow. Changing personal hooks or skill loading is a separate execution-policy decision.

**Settings → Automation → Advanced → Worker time limit** sets the coding-task deadline. The default remains 30 minutes; valid limits are 1–1440 minutes. Overrides select an already known repository by path and host, while matching its exact host and project identity internally. Add an MR to the board or Scope before configuring an unknown repository. The limit is captured from the run's saved configuration for both providers; changing automation settings keeps the existing cancellation/retry behavior and does not silently extend or restart a running task. Verifier and GitLab request timeouts are separate.

The same bounded read recovery applies before automatic approval and workflow admission. A failed preflight read does not mean a remote operation failed. After an uncertain approval response, the app reads the current approval state before deciding whether the operation succeeded; it does not automatically repeat an unconfirmed submission. Validated semantic assessments are persisted before final reads and reused after transport failures or a restart. These pending assessments authorize no publication until fresh source, identity and content checks finish. Automatic publication also waits for queued or running work on the same account and MR to finish; independent valid reply evidence remains available.

When an assigned check needs an installed, configured local runtime that is stopped, workers may start it through its service CLI and verify readiness before reporting a blocker. For an active OrbStack Docker context, they check `orbctl status` and `docker info`, bound startup to 60 seconds, then reconcile local Git state before retrying the failed check once. They do not install tools, change global runtime versions or Docker contexts, edit global hooks, relax checks, reset services, or replay remote writes. Coding-agent GUI integration remains outside the headless task.

## Agent usage estimates

**Settings → Agent usage** compares work started by MergeTether through Codex CLI and Claude CLI. Overall and role cards separate coding-agent work (reviews, follow-ups, conflicts and pipeline fixes) from lightweight verification and classification, with reported input/cached/output tokens and unknown or partial runs. Choose Today, 7 days, 30 days, the current month or all tracked time. Provider bars can group by hour, day, ISO week or month; hover for the bucket's estimate and separate Codex/Claude amounts. The graph shows at most the latest 1,000 buckets and marks truncation; summary totals still cover the entire selected range.

Runs belong to their start hour in UTC, and ISO weeks begin on Monday. Daily history and the known-estimate average include zero-activity UTC days between the first tracked day or range start and the current day; a partial current day counts once. Unknown-only usage has no invented zero-dollar average. Tracking begins with the first new app-owned CLI run; earlier work is not backfilled. Counts, pricing versions and optional account/MR identity, title and URL are saved locally across restarts without prompts or transcripts. Unattributed older records remain in overall totals without being assigned retrospectively. Recent completion receipts are deduplicated; older finished receipts become hourly role/provider/MR totals, preserving all chart granularities. The top-five MR ranking follows the chart’s selected range and current UTC-hour cutoff; MR Details sums all tracked time for that exact host, account, project and MR, independently of the Settings date filter. Its verifier and reviewer / work agent rows show separate costs, reported tokens and **Agent requests**. The work agent includes reviews, author-feedback work, follow-ups, conflicts and pipeline fixes; the verifier includes evidence checks, reply verification and classification. Each app-started CLI invocation with a prompt counts as one request, even when it fails or its usage is missing. A fresh retry counts separately; repeated completion callbacks and cached checks do not add a request. Internal model turns, tool calls and separately opened MR conversations are not counted. No history is inferred for older runs without MR attribution.

Dollar amounts are comparison estimates, not subscription payments or billing receipts. Claude supplies its own [client-side CLI estimate](https://code.claude.com/docs/en/headless). Codex uses reported completed-turn tokens and the [published standard short-context API rates](https://developers.openai.com/api/docs/pricing), captured on 8 November 2026 for the exact supported model IDs. Cached input is already included in input, and reasoning tokens are already included in output. The Codex baseline excludes cache-write premiums, tools, long-context and service-tier adjustments; unknown model rates remain unavailable. Stored dollar estimates retain their original pricing version when app rates change.

Failed CLI exits still contribute reported usage. Failed Codex runs, timeouts, cancellations and interrupted runs retain available partial usage and an unknown/partial count; missing usage never implies zero. A final Claude cost envelope can still report its failed run's estimate. Unrepresentable aggregate totals are marked unavailable. Separately launched nested CLIs may not be included in their parent's reported usage. An accounting read or write error does not stop MR automation; Settings reports unavailable history while keeping any previously loaded totals visible.

## Informational review acknowledgements

On your managed MRs, the accepted-feedback resolution setting also permits a thumbs-up reaction and closure of a purely informational thread. The current verifier must explicitly confirm that the entire thread, including author replies, has no question, requested change, expected answer, outstanding condition or ambiguity. An old or merely informational assessment is insufficient. Mixed threads retain the existing feedback and consent rules; acknowledging a pure thread does not approve a reviewer or accept their other findings.

Courtesy reactions also depend on account metadata and the comment's purpose. Regular human accounts may receive a thumbs-up on safe review feedback or a summary even when AI helped write it. Verified bot or service accounts receive one only for specific, concrete code-review feedback, not generic review summaries, no-findings reports or general observations about code structure. Explicitly generated generic workflow reports and artifact-generation status announcements are skipped even when their posting account has GitLab's regular account type. AI-like writing alone does not identify a bot or an automated workflow. Missing account evidence or a missing, unrelated or unclear purpose skips the optional reaction. These restrictions do not prevent an independently verified safe thread from closing.

The app checks its current account, MR head, discussion text, readiness, drafts and policy before each write. It checks existing reactions first and confirms new ones by reading GitLab again. Draft MRs follow the effective automation policy, and pending private replies retain their existing read-only restrictions. No courtesy text reply or private draft is created. Reactions and thread closure run through the app; headless workers keep their assigned task permissions even when a personal MR instruction allows these acknowledgements outside the app.

A failed optional reaction does not block independent corrections or an otherwise permitted thread closure. If GitLab does not confirm closure and the thread remains open, the MR offers a fresh verification rather than silently repeating the write. A new commit or a change in another thread does not replay that failed operation; a deliberate recheck or a change in the affected thread permits a fresh attempt. Resolved history is skipped, and acknowledgement work is limited to four new threads per pass.

## Task history, failure and migration

Each MR has one collapsible **Automation event log** in its details. It combines numbered worker attempts, workflow events and persisted application decisions with exact timestamps. A gear icon identifies automatic activity; hover for its meaning. Expand an event for its blocker, error and evidence identifiers, or open the linked run for its recorded prompt, response, transcript and run actions. A successful worker can still have a later application rejection; both results remain visible. Application events are bounded to 100 per MR and 1,000 total, and are scoped to the signed-in account.

A feedback follow-up that finds no remaining work can complete without creating duplicate replies only after an independent, current-content assessment verifies the selected notes and required published responses. While a verification of the exact current content is running, the follow-up stays neutral. Its completion immediately reconciles the intent without waiting for a global refresh. Older observations cannot overwrite a replacement attempt. This does not waive the proof required to publish new drafts.

MergeTether persists task instructions and execution state locally, including output and errors. Isolated working files are kept under the app’s local `Assistant Runs` directory and can be revealed from the run, so interrupted or local-only fixes remain inspectable. Concurrent work for the same MR is coordinated. Before ordinary MR work starts, the worker verifies the queued GitLab account and live MR state. Closed or merged MRs do not start review/fix work; failed state checks do not become false completions.

Failed, cancelled and interrupted work stays inspectable. A deliberate retry creates another execution attempt; restarting the app does not silently replay a task that may already have changed GitLab. If a retry is needed, inspect any remote effects first.

Before retrying a pipeline task, the app reads its current MR and pipeline. A passed, replaced or currently running pipeline does not start another repair worker. Current evidence removes only the obsolete pipeline blocker from the board; the original run stays in history, and unrelated feedback or drafts keep their own actions. Missing or inconsistent evidence does not silently retire a failure.

MR menus and Details offer **Refresh from GitLab**. This refreshes tracked data through the normal monitoring path without clearing verification results or retry fences. Details share the card's MR actions and pin control. Automatic monitoring follows the selected refresh interval, with an hourly option available; forced refresh does not add a second periodic timer.

Old GUI handoffs and links remain decodable for migration, but are not automatically replayed. Automation does not create desktop agent chats, append messages, synchronize chat titles, install desktop plugins, monitor listener heartbeats or register permission templates. Explicit manual desktop actions remain available. Previously configured external listeners are outside the app’s control; inspect and disable those schedules separately before using headless automation for the same MRs.

The app bundles standalone proof helpers under `Contents/Resources/Automation`: `evidence.py` and `author_follow_up.py`. They read GitLab state and store local evidence without an installed plugin, MCP configuration or listener. Retired desktop plugin and listener sources are no longer included in this repository; existing external installations and schedules remain under the user's control.

## Optional manual agent actions

An MR’s right-click menu and bottom-right **Actions** button offer the same actions. **Start conversation in…** opens the default app configured under **Settings → General → MR conversations**, independently of the automation provider. Hold **Option** to show **Start conversation with…** and choose an installed desktop app or CLI for one conversation; this does not change the default. The chooser also offers **Copy MR context**. If the default is unavailable, the chooser opens instead.

Desktop actions attach a local UTF-8 text file containing only the MR link and title to a new conversation without a repository, leaving the message field empty. The user writes and sends the first request. Context files remain in the app’s local Application Support directory so the assistant can read them later. CLI actions ask for your message before opening Terminal with it and the minimal MR context; their configured workspace behavior is retained. Without a configured workspace, a CLI opens in a fresh empty folder. Desktop attachments and empty CLI folders both use the installation’s bundle-specific Application Support directory, including custom-identifier installations. These actions do not switch the automation provider or enable automatic desktop dispatch, and MergeTether does not manage the external conversation.

Opening an external destination is not proof that its work completed. A manual session must coordinate ownership before fixing a pipeline already being handled elsewhere. MergeTether’s remote-evidence and publication rules still apply to drafts eligible for automatic publication.

## To-dos become MR actions

To-dos are incoming events. A recognized update for an MR already on the board updates its action state and is acknowledged after that state is persisted. The card shows the resulting action, rather than a separate to-do row. The action and any running or failed agent task remain visible after the GitLab to-do disappears.

A new foreign MR is proposed in **Inbox** with **Add and handle** or **Ignore this MR**. With matching enabled automation, active scope and a ready selected CLI, eligible MRs are adopted and handled automatically. Explicitly ignored or paused MRs are not silently re-adopted. Manual re-addition restores an ignored MR.

A submitted review is handled by its event type and live MR evidence, regardless of the reviewer identity. Open threads on your MR enter the configured follow-up action. General reviewer comments are assessed by the shared semantic verifier before it starts warranted follow-up work; informational summaries do not require code changes. Reviews with no open threads refresh the durable MR state. A failed evidence read leaves the event unread.

A substantive published author reply in another discussion can prove that a shared correction was delivered. The shared verifier names the exact reply ID after checking the concern, current correction and reply body; the app checks that the reply still exists uniquely, belongs to the MR author and is a later non-system comment. Each separate actionable feedback thread, including general comments, still needs its own reply. The worker verifies the current remote correction and prepares a short private draft linking the original feedback or explanation instead of repeating the code change. Simple fixes normally get a brief acknowledgement in the comment's language; additional explanation is included when useful, subject to the user's skills and workflow instructions. Purely informational summaries without a distinct request do not get courtesy replies. Fresh account, commit, context, remote-content proof and draft checks still fence completion and publication. An unanswered thread remains visible as needing a reply and cannot be automatically resolved merely because its reviewer approved.

Events that cannot be classified safely remain in **Inbox** for manual reading; they are never acknowledged as understood. Marking a routed event read does not prove a review finished, a fix was pushed or a draft can be published. Those outcomes keep their separate execution and remote-evidence checks.

## Automation profiles

Choose a profile in **Settings → Automation → Profile & permissions**, then adjust individual permissions. Until automation is explicitly enabled, automatic GitLab writes and worker push or thread-resolution permissions remain off. Missing consent in older settings stays undecided regardless of saved feature flags. Running a review manually permits that review and private drafts; it does not enable later automatic approval, publication, merge, resolution, reactions, to-do acknowledgements or re-review requests. Explicit manual GitLab actions remain available. The page groups preparation, comment publication, delivery and completion. **Review & feedback** retains the trigger and repository rules; **MR Events** retains its event filters. **Advanced** keeps saved shell titles and commands, with their stored enabled/disabled state visible; they do not run automatically. Choosing a profile or migrating a legacy handler to the coding agent remains explicit. The app preserves existing settings across upgrades. New automation setup offers **Max**.

| Profile | Automatic preparation | Publication and delivery |
| --- | --- | --- |
| **Manual** | Automatic task rules and verification are off. | Start tasks and GitLab actions yourself. Explicit **Run review** and manual GitLab actions remain available. |
| **Safe** | Review, verification, private drafts, local follow-up, pipeline and conflict preparation. | No automatic public actions: publication, approval, push, thread resolution, review requests, to-do acknowledgements, CI mutations and merge remain manual. |
| **Trusted** | All supported automatic preparation. | Approve, push fixes, resolve verified eligible threads, request re-review and handle eligible pipeline actions. Publish only eligible replies to AI-assisted feedback. Other comments and every merge wait for you. |
| **Max** | All supported automatic preparation. | Enable all supported automatic delivery, including eligible comment publication and merge, within active scope and the existing evidence, ownership and readiness checks. |

The profile selector appears first, followed by its summary and the detailed permission controls. Choosing a profile immediately fills the working form; **Apply Changes** commits it. Manual and Max have compact summaries; Safe and Trusted list both automatic work and the actions left to you. A matching profile is recognized from the current permissions, independently of the last selected defaults used by reset buttons. Hand-editing the controls to reproduce a preset selects that preset automatically.

**Custom** becomes available after you create a nonmatching configuration. The form retains your latest custom permissions when you try another preset; an explicit save retains that choice across restarts. Choosing a preset does not erase the saved custom configuration. Returning to Custom restores the automation permissions and the profile-controlled AI requirement, while preserving current models, instructions, scope and other repository, author and event filters. Fresh installations with no custom configuration do not offer an empty Custom option. Older saved **With checkpoints** settings retain their permissions; they never acquire Trusted permissions on decode or upgrade.

Global permissions, automatic review and feedback handling, verification, event modes and CI retry permissions are editable on **Profile & permissions**. **Coding agent** retains models and reasoning; **Review & feedback** retains handler details and repository restrictions; **MR Events** retains event filters and timing. These pages do not contain a second copy of the global permission switches.

Safe has an independent public-action boundary. Private drafts and local preparation can continue, but enabling an individual delivery switch does not bypass that boundary. Explicit manual actions remain available. With follow-up push disabled, local code proposals remain in the task result rather than creating completion replies that imply a delivered fix.

Saving a permission change revokes future worker permissions and cancels active work using the previous configuration. An external operation already sent before the change can still complete; changing the profile cannot undo it.

A successful settings write is reported separately from a safety-data hold. Corrupt receipts can keep automatic actions paused even after new settings and Custom history are saved successfully. Failure to remember optional Custom history leaves the previous snapshot available and does not itself change active permissions.

Waiting for review never creates a comment or a draft. After the configured waiting period, the rule can track a local event or stay off. Older settings that ran an agent for this event are migrated to local tracking; queued reminder jobs are retired.

**All eligible comments** is the default publication mode in Max. It bypasses optional publication filters. Trusted uses **Replies to AI feedback**; Safe and Manual use **Private drafts only**. Conditional publication also applies the selected repository and author conditions; nonmatching comments remain drafts. Checked-content, account and remote-evidence checks still apply in every automatic publication mode. Existing saved custom choices are preserved.

Automatic re-review in Trusted can continue after you deliver fixes or publish the pending replies. Local preparation is not evidence that a proposal reached the remote branch.

MR event rules watch failed pipelines, new commits after review, author replies, merge blocker changes, merged stack dependencies and overdue reviews. Configure these in **Settings → Automation → MR Events**. Choose **Off**, **Log a preview**, **Track event** or **Run with agent CLI** for each rule. The two passive modes record activity without starting an agent task; notifications follow the human-attention policy below. Repository, target branch and label filters constrain event rules.

Scope is always required. Empty additional project lists mean all repositories permitted by the active scope; nonempty lists restrict the corresponding tool tasks, conflict pushes or automatic merges to exact repository paths.

Manage global scope and repository/MR overrides in **Settings → Automation → Scope**. Scope changes save immediately. Other automation pages use **Apply Changes**, preserving scope edits made in the meantime. Paused and closed MR overrides remain editable.

An MR's **… → Automation** menu can independently opt out of automatic comment publication, merging or approval. A checked action inherits global rules; an unchecked action is deliberately manual for that MR. These choices neither add the MR to management nor change whole-MR scope. Globally disabled actions remain disabled. Other automatic work continues, and the checkpoint appears only after that action's normal evidence and readiness conditions are met. Restoring Auto immediately joins or queues a fresh automatic check, including while a refresh or confirmation is already running. Publication resumes only individually eligible checked drafts under the current publication policy; it never uses the manual Publish all bypass. Completion of verification is still a normal background refresh event, so other independently enabled automation may continue under its own global and per-MR permissions.

## Board grouping

In **Settings → Automation → Scope**, choose the lower board section: **Without automation** (the default) or **Drafts**. The same choice controls ordering and muted titles/statuses across the board. Without automation uses effective MR/repository scope, including the Draft default; opted-in Drafts remain in the main group and keep their Draft title and badge. Drafts groups every Draft below Ready MRs, without changing action permissions. Pins and normal priority ordering apply within each group; finished MRs remain first. When all automatic features are off, the picker is hidden and Drafts is used temporarily. Re-enabling automation restores your saved choice.

## Local feedback decisions

Details shows the exact author, quotation and note link behind a current feedback finding. Thread roots are not substituted for a different comment that supplied the finding. A stopped worker's selected comments are labelled as scope; a tool failure or failed push is not itself an ignorable reviewer suggestion.

**Ignore this suggestion** opens a confirmation containing the precise concern and source. The saved decision applies to that concern, not the whole comment. Future verifier and coding-agent invocations receive the current list; another requirement in the same comment still needs work or a supported reply. Decisions bind the GitLab account, MR and exact source text, survive restarts and commit changes, and stop applying when that comment is edited. They do not authorize GitLab resolution, approval or publication, nor waive factual reply checks or ordinary merge gates.

The **Ignored suggestions** list appears in Details only when nonempty. **Restore** removes one exception; **Reset all** clears this MR's list. Both start a fresh check and retain history. A deliberate decision change starts a fresh bounded assessment/work context, while ordinary polling retains existing retry limits. A queued worker builds its exception context at execution time; removed decisions are not embedded in stored task prompts, and running coding workers are not cancelled.

## Attention and notifications

## The human checkpoint

**Settings → Automation → Profile & permissions** contains the **Comment publication** selector plus separate approval, push and thread-resolution permissions.

- **All eligible comments** is selected by Max. In this mode, the app waits until drafts stop changing across two refreshes and verifies current evidence before sending them. GitLab cannot identify which agent created a draft, so this can include your own pending drafts on MRs the agent worked on.
- **Replies to AI feedback** limits automatic publication to eligible replies to content written or substantially assisted by AI, including comments posted from a person’s account. An account name alone neither qualifies nor excludes a source. Verified GitLab Duo comments qualify directly; other sources require a high-confidence assessment tied to the source note ID and exact body hash. This is a probabilistic judgment based on text and discussion context. Missing assessments mean unclassified, rather than human-authored. Likely manual, unassessed and uncertain sources keep their replies private. Edited comments and later follow-ups require their own assessments.
- **Private drafts only** leaves comments private until you explicitly publish them.
- Automatic publication rejects slash-command lines and `resolve_discussion`. It publishes checked draft IDs individually, after another read. Unrelated or changed drafts remain private.
- **Review and confirm** on an MR card opens its discussions and draft preview. Checkboxes select exact draft versions for **Publish selected**; **Publish all comments** remains available. Selection starts empty, never includes newly arriving drafts, and is cleared for edited or removed drafts. The selected action stays available at the bottom while browsing long threads. Only selected IDs are published, individually, after current-account and body checks. Changes to unrelated drafts do not enlarge the selected set. These explicit manual actions work without the agent CLI or automation and bypass automatic publication filters. Explicit publication sends the previewed set only if it is unchanged. Publishing in GitLab is also supported; the board refreshes pending confirmations while it is open.

When an AI condition applies, the configured lightweight verification model proactively assesses current source comments that lack a matching result, including while reply drafts or remote verification are pending. It considers text and discussion context, regardless of the posting account, and treats comment instructions as untrusted data. Only a high-confidence AI-assisted assessment can qualify a source; likely manual or uncertain results leave its replies private. Oversized or unavailable text remains uncertain. The app re-fetches current source bodies before saving assessments and reuses unchanged results. Failed and uncertain checks are cached by source body, provider, model, reasoning setting and criteria version to avoid repeating them on every refresh. Assessment does not publish anything or relax scope, draft-content or remote-evidence checks.

The content heuristic combines precise references across code locations or detailed implementation-to-test reasoning with consistent code quoting, author-written line references, polished language and repeated review structure. Em dashes, sentence-ending periods and other punctuation are weak supporting cues and never sufficient alone. Repository knowledge is not evidence of manual authorship. Multiple corroborating signals without meaningful counterevidence can support `ai_assisted` at `high`; `very_high` is also accepted. A likely manual or uncertain classification never qualifies, regardless of its confidence label. Automatic diff anchors are not author-written line references. These are workflow heuristics, not verified authorship or universal probabilities.

Assessments record their criteria version. After a criteria change, older nonqualifying results are assessed again once under the current provider/model/reasoning setting; unchanged current results remain cached. Current qualifying content-bound evidence is retained. This does not change publication mode, scope, remote-fix proofs or other publication checks.

In conditional modes, all active conditions must match (AND). Within an author or repository list, any selected identity qualifies; an empty list adds no restriction. Explicit manual **Publish all** bypasses automation filters. Active scope and the other execution and publication checks still apply to automatic actions.

Repository and user entries are verified through GitLab and stored as host plus stable project/user IDs; their labels are display text. Source-comment conditions check every external comment in the latest incoming exchange: comments after your last reply before the newest incoming comment. Your later replies do not erase those sources. An unknown author, missing discussion evidence or a nonqualifying follow-up keeps the response private. A new finding without a source comment cannot satisfy source-author or AI conditions. AI assessments remain bound to the current source note and exact body.

The board’s automatic-publication preview and the last live check use the same policy. Changing the mode or any condition invalidates the old preview immediately. Publication still uses exact checked draft IDs and all existing draft-content, remote-proof and account checks.

Reset arrows beside the publication mode and checkpoint permissions restore only that setting using the profile you last explicitly chose. For legacy or custom settings without a known profile, the reset menu lets you choose **Manual**, **Safe**, **Trusted** or **Max** defaults for that setting. Resetting one condition restores only that condition; **Reset publication filters** restores the selected profile’s filter defaults. Other permissions, scope, agent choice, custom task instructions and drafts remain as configured. **Apply Changes** saves the policy and immediately starts a fresh MR check; publication follows when the current evidence passes. These conditions apply only to automation: an explicit manual **Publish all** action ignores them.

Draft readiness requires a check covering the current MR head and discussion content. New or edited comments invalidate it; resolution-only changes preserve it. Failed or missing checks leave the drafts visible with an explanation that they need review. Explicit manual publication remains available from the MR details.

## Remote proof for author follow-ups

Known app-origin sealed drafts with incomplete older proof can receive one fresh verification per exact account, MR, draft, discussion, code and verification context. Current automation permissions must still allow it. The lightweight verifier reads live GitLab evidence and checks each draft's claims. It archives independent current proof without changing the original run's result. Each requested draft subset remains bound to its complete historical origin. Verified replies can publish individually while uncertain siblings stay private; refreshing one draft does not adopt or invalidate its unchanged siblings. Unknown origins, edited drafts and uncertain claims remain private. Verification progress is neutral; a failed check shows its reason and a retry action.

Rejected checks remain fenced per exact draft across restarts and narrower batches. Publishing a verified sibling or automatically tracking another MR does not reset that result. Meaningful new claim evidence, such as changed code, discussions or CI, can permit a fresh check; **Verify drafts again** explicitly resets the attempt fence while retaining valid proof.

Verification thinking applies to new model invocations. Changing it does not discard a completed draft-claim verdict, including one awaiting final live checks after an I/O failure. Current evidence and permissions are rechecked before using that verdict. Use **Verify drafts again** to request a new assessment of unchanged claims.

Workers receive a private temporary directory in `TMPDIR`, `TMP` and `TEMP`, and an explicit JVM `java.io.tmpdir` option. A blocked author follow-up with an identified local temporary-file permission failure can receive one fresh automatic attempt while its original commit, account, discussion and active permissions still match. The attempt is persisted before launch and reconciles existing remote changes before doing new work. It preserves the old failure in history; failed, cancelled, interrupted or otherwise uncertain runs are not blindly replayed.

A failed, cancelled or interrupted feedback follow-up can also be reconciled without starting another worker. The current verifier must prove that every assigned note is addressed or informational and any required reply is already published, after fresh account, source, MR context, discussion and draft reads. That proof belongs to the exact stopped attempt and current conversation. It retires the obsolete retry prompt across the board and inbox and releases the historical unfinished-work gate; current feedback, unpublished replies and every approval, CI and merge check still apply. Original execution results remain in history. Reviews, conflict tasks and pipeline reservations keep their separate recovery rules.

A blocked feedback follow-up needs stricter proof: the verifier receives the exact latest eligible run, its selected feedback and actual stopped step. It may retire that run's obsolete attention only after current evidence proves every selected correction or explanation complete, every owed reply published, and the stopped step no longer blocking the assigned MR task. Missing proof, changed run context, unverified required tools or checks, and unrelated work keep the block. The proof binds the current account, commit, MR context and discussions and changes no execution history. It removes only the obsolete stopped-work gate: configured automatic merge may continue when every ordinary approval, pipeline, scope, Draft, commit and discussion check passes. It grants no independent approval, merge or deployment permission.

**Let the agent push fixes to my merge requests** is enabled by Trusted and Max and is independent of conflict-push permission. Turning it off is preserved across restarts. Installed MR skills can refine the work, but are not required for this sequence.

The worker runs the bundled `author_follow_up.py status` command at the start and immediately before pushing. Only an explicit author-follow-up run carries that permission; review, legacy and conflict tasks cannot inherit it. Before drafting it runs `author_follow_up.py verify` with the run ID, tested/pushed commit and an evidence file containing the assessed discussion fingerprint and SHA-256 hashes of committed source/test files. The verifier reads the authenticated user, owned MR, source branch and remote file contents.

Only after verification may the worker save/refetch reply drafts and bind their IDs and exact body hashes using `author_follow_up.py seal`. Preflight tokens are one-use. Sealed receipts are archived separately per verification, so a later task cannot replace proof for earlier unpublished replies. Publication rechecks each reply against its exact known origin, current source and draft body; newer unfinished work still blocks automatic publication. Known older sealed run artifacts can be recovered, while unknown or unsealed drafts remain private. Existing user-created or legacy drafts cannot be silently adopted. A previous sealed draft can be rebound after fresh verification when a later stacked fix changes the remote head. The bundled standalone `author_follow_up.py` helper supports this evidence flow without desktop setup.

Automatic publication rechecks the account, current run, push permission, source branch, remote head, file content, discussion fingerprint and draft body. Missing or stale evidence keeps replies private even under publish-all. Existing drafts are never deleted or rewritten by this gate. Worker-written preflight and seal files remain untrusted origin candidates. Successful fresh semantic recovery records are authenticated by the app using its protected completion-journal key; unsigned or modified assessment files cannot authorize automatic publication. Known legacy candidates may be reassessed, while old unauthenticated results need fresh verification. This detects later record substitution; it does not make a full-access worker or its chosen source-file claims inherently trustworthy.

When the source HEAD changes, known app-created reply drafts can receive a fresh, read-only claim assessment automatically. Their recorded IDs and body hashes are checked against the app-known run/account context, while source-file hashes and the assessment are collected again at the new HEAD. Only individually valid replies gain current proof; publication still applies the current AI, author and repository conditions. Uncertain or invalid claims and drafts outside those conditions stay private. Unknown or edited drafts are not adopted, and a second head or discussion change during verification invalidates that attempt. Rechecking does not rerun the coding worker or rewrite any draft.

The verifier proves the selected committed files reached the remote revision. Meaningful tests, sufficient file selection and claims matching the changes remain the worker’s responsibility. GitLab has no conditional draft-publication endpoint, so a small race window remains after the final check; checks are repeated immediately before sending.

## Re-review readiness

**Settings → Automation → Coding agent → Re-review verification** is on for Safe, Trusted and Max, and off for Manual unless explicitly changed. It uses an independent verification model: Luna for Codex and Haiku for Claude by default.

**Verification reasoning** is shared by Codex and Claude across feedback verification, draft-claim checks and AI-assistance assessments. It offers Low, Medium and High, with High as the default for new and existing settings. Explicit saved choices are retained, including when applying a profile. The reasoning choice is separate from the coding agent’s reasoning setting.

The verifier receives the MR target, expected commit, source note IDs and semantic context, with bounded, credential-filtered title, description, diff and discussion evidence when available. It can use `glab` to read the current MR, paginated discussions, diffs and relevant files. Large inputs can use target metadata instead of failing only because inline evidence exceeds the limit. It classifies every external non-system comment, including general comments, and returns reasons tied to note IDs. Informational summaries require no answer. A concern blocks its reviewer; unrelated feedback need not block another reviewer whose concerns are addressed. Unsupported author claims are not proof, and missing evidence stays uncertain.

Once all current feedback is verified as addressed, informational or explicitly ignored, and all required replies are published, re-review also includes assigned human reviewers who participated earlier or whose approvals were reset. Re-review eligibility uses the current GitLab reviewer list and is checked again before sending. A participant who leaves that list receives no re-review request; adding them back restores normal eligibility under the existing readiness and exclusion rules. Re-review never adds an absent commenter to the reviewer list. It uses GitLab's re-request action rather than posting reminder comments. Current approvers, bots and inactive accounts are excluded; assigned people who have not participated receive no extra request. An outstanding or in-progress review is kept, and requests are deduplicated by source commit and reviewer activity across restarts. Earlier reviewers wait while any feedback remains blocking or uncertain; individually addressed reviewers retain their existing per-reviewer readiness checks.

A reviewer’s explicit request to stop participating is assessed against an exact quote from their current comment. A pure opt-out needs no code change, reply, acknowledgement or reaction, and excludes that participant from re-review. Any genuine technical concern in the same comment still needs assessment and correction; an opt-out never supplies acceptance or permission to resolve a discussion.

**Settings → Automation → Advanced → No automatic replies or review requests** stores explicit exclusions by GitLab host, signed-in account and stable participant ID. These exclusions apply to automatic replies, acknowledgements, reactions and reviewer invitations, including final write checks and worker instructions. They can be reversed with **Allow again**. Changing them invalidates affected readiness evidence without changing the automation profile. Existing drafts and history remain intact; manual checked publication remains a separate user action.

The verifier correlates review summaries with the concrete findings they reference across discussions. A verified correction or substantive answer in the matching thread avoids a duplicate answer in the summary; distinct requests or remaining conditions still block readiness. Informational classification does not grant reviewer acceptance or consent to close referenced findings, and a summary awaiting reviewer reconsideration stays unsafe for informational closure.

Workers and verifiers distinguish an observed defect from a reviewer's proposed remedy. Rejecting an unsupported remedy does not settle an independently supported defect. The coding agent researches accessible contracts, related callers and tests, and can implement a warranted correction using established behavior without inventing an undocumented business meaning. A genuine external decision remains an explicit, concrete question after that evidence has been checked; routine research and code work stay with the configured agent.

A prerequisite for a later rollout, deployment or organizational step is not unfinished MR work merely because third-party confirmation is absent. A verified correction or supported explanation with the required published reply can wait for the reviewer without another worker or duplicate answer. Explicit requirements before merge, actual unresolved defects and decisions needed to perform the current assigned work remain blocking. Neither worker nor verifier may invent external acceptance. Assessment-policy changes and changed blocked-run context invalidate the corresponding session cache.

These assessments support re-review requests and the accepted-feedback checks below; they never themselves authorize a GitLab write. The output schema requires one result for every external comment ID, including resolved comments, and the app independently rejects duplicates or missing evidence. Read-only evidence gathering uses up to three attempts with two- and eight-second backoff, followed by a fifteen-minute cooldown after exhaustion. Each verifier invocation can also retry failed or incomplete provider output once. These retries retain full read-only CLI tools and never replay an executable MR task or remote write. Results are reused for unchanged inputs during the app session and invalidated by account, head, discussion, provider, model or reasoning-setting changes. Exhausted failures remain visible, with a deliberate retry available; a later poll can retry after the cooldown.

When verification fails or is unavailable, the MR shows the reason and **Verify again**. If no other feedback or draft blocker is known, **Confirm readiness and request re-review** allows explicit manual confirmation. That confirmation binds the displayed head/discussion content; the app rechecks the live account, scope, MR state and drafts before notifying reviewers. With automatic verification off, manual confirmation remains available, but other agent automation still requires a signed-in CLI.

## Accepted feedback on your own merge requests

**Settings → Automation → Profile & permissions → Resolve addressed feedback after reviewer acceptance** is enabled by Trusted and Max and disabled by Safe and Manual. Existing explicit settings are preserved until a profile or permission is changed. It applies only to your own open MRs within the effective automation policy, including explicitly enabled Drafts and requires the signed-in selected CLI.

This switch controls automatic thread resolution. Turning it off still permits semantic verification and configured author follow-ups; it does not remove the feedback check required for automatic merge.

The verifier checks the current MR title, description, diff and every external comment, including general comments and conditions in other threads. A reviewer's current approval is consent to close their verified addressed threads; it is never proof that their requests were fulfilled. An advance approval such as “approved, but still do X” remains blocked until the request is implemented or substantively answered with a justified explanation. Warranted work enters the configured author-follow-up workflow, with its existing push and publication permissions.

A later explicit acceptance comment by the same reviewer can also provide consent. It may be a general summary covering several findings. The verifier must tie it to the current code and concerns; the app checks the cited note's author and chronology. Generic thanks, another person's approval, stale acceptance and account-specific exceptions do not qualify. Every actionable participant in a thread must be satisfied, and missing evidence prevents resolution.

When a current, complete assessment confirms that your work and replies are finished, a remaining GitLab request for changes means the MR is waiting for the reviewer. It does not by itself create another author coding task or human Attention item. GitLab's approval and merge restrictions still apply.

Before each resolution the app rechecks the live account, owned MR, source head, MR title and description, entire discussion text, current approvals, drafts, settings and scope. Pending replies must be published first. The MR detail shows remaining corrections or explanations, unpublished replies, verification failures and reviewers whose acceptance is missing. A reviewer who has already accepted is not asked to review the same unchanged feedback again. Changes to the MR title or description invalidate semantic assessments even when the source commit and comments are unchanged.

Each automatic follow-up attempt records the reviewer note ID and content revision separately from visible job history. An agent reply, new commit or cleared history alone cannot replay that attempt; edited or new reviewer feedback can start new work, and explicit manual retries remain available. Large sets are handled in bounded batches. Stale live evidence triggers a fresh poll; actual verification/API failures remain visible for deliberate retry rather than automatically repeating uncertain remote work.

A successful follow-up also invalidates any semantic assessment made before that run completed. If a fresh assessment independently identifies concrete remaining author work or supplies a valid source-bound technical question, the app can schedule one scoped reconciliation per original run and reviewer-note revision. It requires current account, source, discussions, settings, scope and push permission. An unchanged source is bound to the original expected commit; delivered source changes require that run's matching remote-content proof. The successor receives the specific residual evidence and reconciles prior remote work before editing or drafting. Its durable budget survives restarts and cleared job history, and descendants inherit it. Generic uncertainty, missing replies, unavailable evidence, a newer failed attempt on that concern or an active worker cannot by themselves trigger this reconciliation; existing draft and publication checks still apply.

Private code questions stay separate from the source comment's assessed state. Each quotes exact source context and names a bounded technical question; an additional observation is never attributed to the original reviewer. Both the first worker and a permitted scoped reconciliation receive the verifier's question and original assessment. The existing **Handle feedback on my merge requests** option (or an enabled matching discussion workflow) controls automatic handling; when it is off, the existing manual checkpoint remains and no extra reviewer session is started automatically. Codex uses the configured coding model/thinking, and Claude uses its CLI model configuration. No extra reviewer process or permission setting is introduced.

The reviewer/fixer must confirm or disprove each hypothesis with current code evidence, then fix only a meaningful in-scope defect under the ordinary ownership, scope and push rules. It records the disposition separately in its task result; it does not create a new discussion or reply solely for an additional private observation. With push off, pending or failed, proposals remain in that result. Its completed report returns as supplementary evidence to the final verifier, which still checks live source and required author replies. A pending private code question holds automatic readiness independently of an already addressed source comment; failed or blocked work keeps its existing gates. Rewording a question or polling/restarting does not renew the original note's reconciliation budget. A deliberate manual run retains the existing retry behavior.

**Merge when ready** waits until every explicit GitLab dependency is **merged**. Open, Draft, locked and closed-without-merging dependencies keep it on hold. A branch-stack parent also blocks a child, regardless of the parent's author. Missing, hidden, failed, stale, incomplete or ambiguous dependency/stack evidence never authorizes an automatic merge. These checks apply to polling and restoring a per-MR merge preference to Auto; global, repository and per-MR permissions still apply.

A child must not merge into its parent's branch. After the parent merges, a non-default target still matching that parent's source branch remains on hold, including after an app restart. MergeTether checks historical MRs for that target branch as well as the open stack. A reused branch with a historical MR is conservatively held for target review, even when it could be a legitimate release target. An ordinary non-stack release target with no matching MR remains eligible. Details explain the hold. The existing stack follow-up prepares a rebase/retarget plan; the user reviews and changes the remote target. Enabling automatic merge grants no retarget permission.

Readiness uses fresh dependency snapshots rather than the cached dependency row. Immediately before the merge write, MergeTether checks them again and verifies that the source and target context still match. GitLab's merge SHA condition protects the source; its API provides no atomic condition for dependency or target changes, so a small race remains after the final reads. Desktop and remote **Review merge** actions open the MR details. The explicit **Merge now** or **Set to auto-merge** action performs its own fresh preflight and confirmation independently of background automation.

Automatic merge also requires a fresh complete semantic assessment when external feedback exists. A remaining condition in a general comment blocks it even when GitLab's approval rules are satisfied and every resolvable thread is closed. Turning off thread resolution does not bypass this merge check.

### Explicit merge and GitLab queues

Manual merge is limited to your own open, Ready MRs with current GitLab merge permission. It uses the same source/target, dependency, draft, semantic feedback, published-reply and unfinished-work checks as automatic execution. Turning off global automation, pausing an MR or opting out of automatic merge does not remove this deliberate action. Automatic execution retains its existing scope, project, per-action and policy gates, including conservative approval-freshness checks after agent write capabilities. An unreadable approval-reset policy means unavailable evidence, not a known disabled setting.

Project metadata selects immediate merge or a merge queue. Auto-merge requires a server version supporting the documented `auto_merge` parameter (17.11+). Train projects use the SHA-bound [merge trains API](https://docs.gitlab.com/api/merge_trains/) explicitly; supported ordinary projects waiting on a known active pipeline use `PUT /merge` with `auto_merge=true`. Failed, manual and unknown pipeline states remain blockers. Missing capabilities never trigger a guessed fallback. The implementation contract was checked against the [GitLab 19.5.3 train API source](https://gitlab.com/gitlab-org/gitlab/-/blob/v19.5.3-ee/ee/lib/api/merge_trains.rb) and current REST fields. An enqueue response is followed by a fresh MR/train read and is reported as queued or in train, never as a completed merge.

A persistent receipt is saved before submission. An ambiguous response, timeout or lost postcondition does not permit a blind replay, including after restart. Observed user-created queues are recorded separately, so their disappearance does not silently authorize an automatic replacement. The app never cancels or replaces queued work. A removed queue or changed checked context gets an explicit GitLab checkpoint. Existing polling compares source, target, semantic/discussion content and automation settings against the receipt; changed evidence is shown for review. GitLab controls the delegated queue between refreshes. Its SHA precondition does not atomically bind future comments, target edits or app settings, and the app cannot guarantee cancellation when new feedback arrives or scope is disabled. Review such a queue in GitLab. Existing CI, conflict and feedback repair permissions remain separate; merge grants no retarget or push permission.

Fast-forward trains can fail while replaying an intermediate commit even when the MR's final trees are mergeable and `has_conflicts` is false. MergeTether recognizes the latest GitLab system removal note only for the exact source, MR train ref and current target branch head. An active queue wins over historical failure evidence. A synthetic train base containing other MRs does not authorize repair against those branches. Missing target evidence holds readiness. Cards and Details link the specific train rebase failure; the separate conflict settings can prepare its resolution even when an earlier merge outcome remains uncertain. The worker must reproduce commit replay, then verify actual FF/train preparation on its proposed result before a permitted normal push and again from the verified remote source and current target afterwards. A clean final-tree merge is insufficient, and rewriting published history still requires explicit user authorization.

New train attempts save the last observed note ID before writing. A newer, exact-context rejection can be recorded as proof without deleting the attempt or replaying the same source. Only that proof plus a changed source head permits fresh merge checks after repair. Lost responses without rejection proof, legacy attempts without a note baseline, and unchanged source heads retain their conservative checkpoint.

## Automatic approval

**Approve merge requests automatically** is enabled by Trusted and Max and disabled by Safe and Manual. Approval requires:

- a no-objections verdict for the current MR head and discussion content, bound to the authenticated account and exact app-managed review run and matching its authenticated successful completion;
- no pending drafts;
- every discussion resolved, including other reviewers’;
- an open MR you review, within the effective Draft/automation policy, which you have not approved yet;
- the selected CLI ready for automation.

Approval is pinned to the checked source SHA. A new or edited comment invalidates the verdict; resolution-only changes preserve it. If GitLab refuses automatic approval, the app stops retrying that commit and retains the manual **Approve** action. Disable approval for an individual reviewed MR in its detail controls or automation scope settings. On someone else's MR, resolution remains limited to your own verified review findings; accepted-feedback resolution applies only when you own the MR.

Publishing an unchanged draft captured in that authenticated review completion can preserve the verdict. The app confirms the exact newly published notes and unchanged existing discussion text before authenticating the resulting fingerprint. Later or edited drafts, direct comments and unsigned draft-history caches cannot extend automatic approval under an older review.

Old account-less or unbound verdict files do not acquire automatic-approval authority during migration. They require a current app-managed review. This authenticates the origin of the review result; it does not add an independent second review or make the review worker's judgment infallible.

The account, MR, source, target, old pipeline and exclusive reservation are rechecked; a durable attempt is saved before the request, and an uncertain reply is never blindly retried. Full CI traces stay out of the preparation prompt. Infrastructure job retries still need a listed project and verified current pipeline evidence. |

The small **Automation** lightning button shows the MR's effective automation state. Click it to choose **Always on** or **Always off**. The **…** menu offers **Auto**, **Always on** and **Always off**, plus the repository default. Auto follows the existing scope and Draft policy; forced choices persist across Draft/Ready changes. They never grant globally disabled workflow, push or publication permissions. Pausing automation keeps the MR on your list. A small marker distinguishes forced modes, and hover help explains the mode and source.

**Pause automation for Draft MRs**, under Settings → Automation → Scope, defaults to on for new and existing settings. In Auto, Drafts are tracked without automatic agent assessment, reviews, publication, fixes, conflict work or CI actions. Factual catalog/dependency reads and recording accepted to-do events are tracking. Turning this preference off or choosing Always on permits the same configured work as on a Ready MR. Existing legacy MR opt-ins remain Auto and do not bypass the new default. Drafts never merge automatically, and headless workers must preserve Draft/Ready status.

Changing a Draft to Ready under Auto resumes the existing configured rules; changing it back pauses them. Always on/off ignores readiness transitions. **Mark ready** is a separate manual action for your own open Draft, with fresh account, ownership, head and result checks. It can resume configured automation. Ordinary manual actions remain available on Drafts, subject to their normal prerequisites. When all automatic features are disabled, per-MR/repository automation controls and Draft automation preferences are hidden; manual GitLab actions remain available.

Saving automation policy or scope changes synchronizes proof permissions immediately. Scope changes cancel only automatic work for targets that are now inactive, preserving unrelated and manually started work. Other automation policy changes cancel active app-owned agent work. Historical script execution remains internally compatible, but is not an available MR automation mode. Remote actions are rechecked at their relevant boundaries; actions already accepted by GitLab cannot be undone by cancellation. Manual actions remain explicitly user initiated.

## What the agent sees

Prepared diff and discussion excerpts filter common credential patterns. Worker tasks can also read files and live GitLab data through their full tool access; these later reads are not covered by the preparation filter. The verifier can also read live evidence through its CLI tools; those reads share the same provider and data-sharing considerations. Scope automation to repositories you may share with the chosen provider. Settings, task history and results are stored on the Mac; task content and data read by the worker can be sent to the CLI’s provider.

## Coordinating pipeline work with another session

A manually started task can reserve an MR before attempting a fix by creating the same local directory atomically. Use the same installation storage root as the running app; the fallback below is the release installation. Replace the host, project ID and MR IID:

```sh
mergetether_storage_root="${MERGETETHER_STORAGE_ROOT:-$HOME/Library/Application Support/com.vaporpw.GitLabTodos}"
claim="$mergetether_storage_root/Pipeline Work/host-gitlab.example.org/project-123/mr-456/active"
mkdir -p "$(dirname "$claim")"
mkdir "$claim" || exit 1
# Keep the reservation until this task finishes.
rmdir "$claim"
```

Remove only a reservation created by the current task. Trusted and Max check these reservations and claim unowned pipeline work atomically. With the automatic pipeline ownership permission off, unverified ownership requires confirmation. Existing failures are discovered on the first enabled poll and persisted pipeline identities prevent replay across restarts. Interrupted runs can leave a reservation; inspect the associated execution before clearing it. A pipeline-refresh attempt is stored separately before requesting current-target CI, including when the server response is uncertain.


New app-owned reservations record the exact installation, run, reservation token and process session. Startup may recover only a precisely matching known terminal run whose recorded app process is definitively dead; active, interrupted, unknown, reused-PID, foreign or suspicious filesystem entries remain held. Immutable pipeline receipts are retained. Legacy shared reservations and receipts remain read-only negative deduplication checks, never current proof of authority. There is no age-based expiry or automatic deletion of unknown locks.
