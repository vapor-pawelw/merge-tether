# Automation and permissions

MergeTether is a local MR command center. Manual GitLab management works without a coding agent. All agent automation requires a compatible, signed-in Codex CLI or Claude CLI; the desktop applications are optional. Tasks run headlessly, with their progress, results and failures available in the main window. Up to four different MR workers run concurrently, with a single worker per MR. Persistent login and quota banners pause unstarted work for the affected provider. Login opens in the default terminal; explicit retry releases queued work, while stopped runs require their own deliberate retry.

Worker output is written to private files throughout execution. Validated complete results receive an account/run/head-bound completion checkpoint authenticated with a Keychain-held signing key and stored outside the worker directory, recoverable at startup. Ordinary Quit cancels worker process trees and waits for cleanup and persistence. Incomplete work remains Interrupted with retained files; raw partial output never establishes success or authorizes a remote write. CLI session persistence is disabled. Retry starts a fresh task, inspects the previous run and re-fetches current GitLab commits, discussions and drafts before continuing; existing work must not be duplicated. Force Quit bypasses that shutdown sequence.

## Product rules

| Situation | Expected behavior |
| --- | --- |
| Trusted or Max reviews an MR within its configured scope. | The preset enables automatic approval. The selected findings threshold and a review of the current diff decide eligibility. CI and diff size belong to separate checks. See [Automatic approval](#automatic-approval). |
| GitLab fails to respond while checking a completed worker run. | Only that MR waits for the audit. The app retries the read, and other MRs can continue. Confirmed unexpected changes require resuming the affected MR. See [CLI setup and execution](#cli-setup-and-execution). |
| A reply needs a source comment’s AI assessment. | Reuse its current sealed action assessment for the same account, content and criteria. A reply worker can supply the first assessment. See [Message authorship in Details](#message-authorship-in-details). |

## How a merge request moves through MergeTether

**When you are the reviewer**

1. A review request arrives. Draft MRs are tracked in Reviewing; their automatic work waits by default, while normal manual actions remain available. The selected CLI reviews ready MRs and saves warranted findings as private GitLab drafts.
2. Drafts wait on the relevant MR card. Open **Review and confirm** to read the complete discussion and private drafts, then publish the reviewed set or edit it in GitLab. Publication can also run automatically under the selected profile and publication mode.
3. New commits, a changed target or author replies can trigger a new re-review task. The first poll establishes a baseline; later events are deduplicated across restarts.
4. The agent checks each concern against the current remote head and records open or uncertain findings in the review verdict. It drafts a follow-up in your thread only when there is a substantive incoming reply that warrants an answer. With **Resolve my verified findings during re-review** enabled, it can resolve verified findings in threads whose first non-system note belongs to you. Turning the option off leaves resolution to you.
5. Automatic approval requires a current review of the same target branch and diff base that meets your selected approval threshold, completed comment review and no pending drafts, in addition to your automation scope and CLI readiness.

In a thread started by someone else, the review worker drafts a reply only when direct evidence shows that a proposed solution, argument or factual claim is wrong in a way that could materially affect a technical or review decision. Acknowledgements, confirmations of fixes, minor corrections and uncertain disagreements stay in the review verdict or run result. The same rule applies to bot threads.

**When you are the author**

**Settings → Merge requests → Treat MRs assigned to me as mine** is on by default. It applies whenever your signed-in account is an assignee, including when other assignees are present. These merge requests appear under **Mine** and follow your configured author workflow, including fixes, pushes and merges when the active profile and project scope permit them. The app rechecks the assignment on live reads before author actions.

Repair summaries, conflict reports and pipeline-fix reports belong in the task result, not new self-review discussions. Workers save warranted replies in the existing incoming reviewer thread. Automatic publication on your own MR requires that incoming exchange in every publication mode, including **All eligible comments**. Automatic reply repair also requires incoming feedback, independently of publication mode; standalone drafts stay private and are preserved for an explicit manual decision. If no reviewer reply is owed, a delivered repair still needs tests and remote-head/content verification, then completes without drafting or sealing an empty draft list. Mac cards prioritize outstanding feedback over merge readiness, and human decision questions remain accessible without an assistant; detailed verification and thread-resolution controls remain in Details.

The feedback verifier first identifies whether each comment asks for a change, answer or other action. Pure no-findings reviews, praise and acknowledgements are informational; prose requests, questions and conditions remain actionable. It reads each active thread before classifying it. Resolved threads stay out of follow-up. A published author reply in a resolved finding can answer the active overview of the same review when the verifier confirms that the reply and current code cover the whole overview and it adds no independent request. For large inputs, the verifier drops the inline diff first and retains descriptions and discussions whenever they fit. It lists exactly which inline fields were omitted for size, then reads live GitLab evidence using the exact supplied MR and external note IDs. These checks have a bounded ten-minute deadline per attempt for live evidence reads; fully inline checks retain the three-minute deadline. Intentional omission is not evidence of missing or changed discussions; failed live reads still leave verification uncertain.

1. Review feedback arrives. The agent handles existing incoming reviewer comments and verifies the relevant fixes and replies; it does not perform a fresh general review of your own MR or create merge requests. The comment verifier can privately escalate a specific technical question to this same stronger reviewer/fixer, including a potentially important defect incidentally noticed in the relevant code path. The agent independently confirms or disproves that hypothesis before making a warranted correction. It implements warranted fixes in an isolated worktree, tests, commits and pushes when follow-up push is enabled. It is instructed to keep work inside its run directory and leave other checkouts alone; this is a workflow rule, not a filesystem sandbox.
2. Before saving completion replies, the worker re-fetches the MR HEAD and verifies the remote source/test content. With push off, pending or failed, the proposal stays in the task result and no completion drafts are created.
3. Verified replies wait on the relevant MR card or qualify for the selected publication rule. MergeTether requests another review only when feedback is ready and unpublished replies no longer block it.
4. Failed pipelines and conflicts can become separate tasks. Trusted and Max check existing reservations and atomically claim unowned pipeline failures. Safe keeps external CI actions manual; pipeline ownership remains independently adjustable.
5. Automatic merge is enabled by Max and disabled by the other profiles. It checks ownership, scope, approvals, discussions, pipeline, the source commit, dependencies and the stack target.

Reviewing cards show the MR author by display name (hover for the account handle), the review-request source when known, and participation in your review threads. Historical replies in resolved threads do not count as pending work. Each card explains the next step and offers an action where needed; queued reviews and verification show automatic progress, while waits on other reviewers remain neutral. Without a recorded request source they say **Tracked for review**; missing discussion data is shown honestly rather than implying a first review. Proposals show the MR author and originating event.

When a current-head review verdict no longer covers the MR title, description or discussion text, the workflow can recheck it once for that evidence context, including after a restart. This uses the existing review-update rule and respects its execution mode and scope. Known published private drafts do not invalidate their own review, and resolution-only updates do not trigger another attempt. Once a fresh review covers the current text, later edits can start a new attempt even if they restore earlier wording. Automatic approval still requires the current verdict and all existing discussion and policy checks.

When an automatically requested review process succeeds but its result cannot be verified, MergeTether can start one recovery for that request after private drafts are handled. Both review rules and the MR's scope must permit it. Recovery checks the prior run's evidence against the pinned live commit, then covers any unverified code or newly changed active discussion text. The attempt survives restart and a fresh, authenticated verdict can complete the original request. New or edited feedback in other active discussions can trigger an incremental re-review while your own finding is open. Resolved threads stay outside that review's scope.

**Review and confirm** places private drafts with checkboxes and expanded original threads directly under the publication controls. All drafts present when Details opens are selected by default; closing discards the selection, and reopening selects the current set again. New or edited drafts are not silently selected during an open session. The MR card’s separate **Publish all and continue** action ignores this window-local selection, but publishes only the exact displayed draft IDs individually. New drafts arriving after its check are excluded. Manual publication waits while an agent is preparing drafts, and checks the current account, source and discussion context before sending. Other discussion history remains below without duplicating pending drafts. An **AI** badge indicates a verified agent identity or a high-confidence assessment bound to the current note and its content. **Human** and **AI uncertain** are separate assessed outcomes. No badge does not prove manual authorship; the badge does not authorize publication or resolution. Clicking (or tapping on iOS) a badge records your own verdict for that exact comment, or for every published comment of a thread after a confirmation. It replaces the assessment for display and for AI-reply publication until the comment is edited or you choose **Use automatic assessment**. A verdict that would let automation publish drafts takes effect only after a 10-second undo window; a verdict that narrows publication applies at once.

Each private draft has a **Delete draft** action with confirmation. Deletion applies only to the exact displayed draft after fresh account, MR and draft checks; an edited draft must be reviewed again. Other drafts are preserved. Deleting a draft never approves the MR, resolves a discussion or changes the recorded review verdict.

Use **Regenerate…** on a draft, in an MR's draft section, or in the board toolbar. The Mac runs the configured assistant with the current local skills and any additional instructions typed on the Mac for this run; they only shape the wording and never extend the task's read-only limits. A paired iPhone can choose only a fixed rewriting style. You can close the sheet while the assistant works and reopen it from the toolbar. Review the original and proposed text, then save the proposals you choose. Drafts without an exact MergeTether authorship record start unselected in a batch.

Regeneration keeps the existing draft ID and anchor. Before replacing a body, the Mac checks the current GitLab account, MR, commit, discussion context and exact draft. Changed drafts require a fresh proposal. The assistant returns proposed text, and the app performs the draft update after confirmation. Regenerated bodies require deliberate publication even if the MR normally publishes automatically.

Once comments have been presented for review, MergeTether remembers a **Finish comment review** checkpoint for that account and MR, including across restarts. Deleting or publishing drafts in GitLab does not finish it: the user could still be composing another comment. After the drafts are handled, **Finish comment review** appears directly on the MR card on macOS and iOS, as well as in Details. It checks the displayed commit, MR context, discussion content, current account and a fresh empty draft list. New drafts or changed evidence keep the checkpoint pending. Details explain which subsequent approval, re-review or merge checks it blocks. Read-only assessments and independent feedback, commit and pipeline work can continue.

**Publish all and continue**, or publishing the complete selected set, can finish comment review after successful publication, an unchanged reviewed context (allowing only the new own comments just sent), and a fresh check that no drafts remain. Partial or uncertain results keep the checkpoint. Successful automatic publication can finish it under the same checks without an extra click. Completing comment review enables the existing readiness checks; it does not override missing approvals, unresolved discussions or review concerns. Older paired phones can still read the board without receiving action types they do not support; the new direct comment controls require the updated iOS app.

Automatic completion also requires proof that the automatic workflow published every draft observed during this checkpoint. If a user deletes or handles any of them elsewhere, automatic publication of the remaining drafts keeps **Finish comment review** pending. This evidence survives a restart. Completion reads are bound to the account and review revision, so a read from an earlier checkpoint cannot change a newer one. Before clearing a checkpoint, the app rechecks the MR, discussions and drafts for changes that arrived during the first read.

An MR has local task history. A process reporting success does not prove that a fix reached GitLab, a review remains current or a pipeline passed. A follow-up worker finishes its part after the required fix, verification and sealed private replies; publication and reviewer acceptance are subsequent steps. Historical blocked workers with complete sealed reply records can enter independent current-source verification without rewriting their execution history. A later sealed blocked result at the same source revision does not strand other owned replies. Missing seals, failed or active work and mismatched source evidence retain their existing fences. A raw worker seal is only an origin candidate; app-known run/account context, fresh source, discussion and claim checks and the configured publication policy still apply.

Pending drafts do not prevent a read-only check of existing feedback or configured follow-up work for independent incoming comments. A private reply prevents duplicate follow-up in its own discussion; unrelated and user-created drafts remain unchanged. Enabling automation for a paused Draft MR, disabling the global Draft pause, or enabling a repository default while that pause is off first asks for confirmation explaining the work and permissions involved. Cancelling keeps the previous policy. Draft MRs default to tracking-only; an effective Always on choice or a disabled global Draft pause enables their configured work. Any pending private reply still prevents automatic discussion resolution and re-review requests. A historical unbound follow-up can close once its own current requirements are addressed and required replies are published, even while unrelated drafts or feedback remain. The assessment itself never fixes code, pushes or publishes replies.

If an existing app-created reply makes an unsupported claim, configured feedback automation returns that exact reply to the selected coding agent. It can correct its wording or implement and verify a justified fix under the existing push permissions. It does not start a new review of your own MR. Repairs retain their original discussion and draft identity; user-created or changed drafts are excluded. An independent current-content check and the publication policy still decide whether the corrected reply may be published. Automatic repair attempts are bounded and recorded across restarts.

A reply that still needs a decision is identified as a **Prepared reply**, with its exact text and a link to the source discussion in Details. Technical verification evidence stays collapsed. A rejected statement is distinct from a failed attempt to fetch current evidence.

Incoming mentions without a known action may receive a read-only semantic assessment using the selected lightweight model. Only a proven informational event is acknowledged automatically, after a fresh account, MR and discussion check. Ambiguous or actionable notices stay available to read. Handled-event banners follow the existing optional banner preference.

Bot authorship is separate from the AI-origin labels on comment text. MergeTether recognizes positive GitLab bot/service-account metadata and explicit entries in **Settings → Automation → Advanced → Bot accounts**. The local list resolves a username to its stable GitLab ID and belongs only to the current host and signed-in account; removing an entry restores GitLab's account classification. Names, comment style and an AI-assisted label do not declare a bot.

When all feedback is verified, required replies are published and the existing automatic-resolution checks permit a write, bot participants do not need a human approval or acceptance reply. Mixed discussions retain every human participant's acceptance requirements, and excluded participants retain their communication restrictions. Bot declarations never satisfy GitLab approval rules or merge prerequisites. Automatic re-review invitations continue to use the current reviewer list and skip bot accounts. Details distinguish addressed feedback waiting for named human authors to resolve their threads from separate outstanding approvals. Bot badges and text-origin labels update as display metadata; they do not renew action permissions.

## CLI setup and execution

Choose **No coding agent**, **Codex**, or **Claude** in **Settings → Agent**. **Apply Changes** saves the choice for manual agent actions and automation. When switching to an agent, setup verifies the executable, supported headless options and sign-in before saving. For a missing or incompatible CLI, setup opens the provider’s installation guide. Follow the guide and choose **Check again** when the CLI is available. Sign-in opens Terminal. **Revert Changes** restores the saved choice in the form.

The coding and verification pickers show recommendations for their respective roles. Select **Show non-recommended models** to see all models supported by MergeTether for that agent in both pickers. A selected model stays visible in its picker until you choose another one.

The CLI requirement applies even when automatic re-review verification is off. Desktop installation does not establish CLI readiness. Dependency checks run independently of GitLab polling. An action that needs an agent offers to open the agent settings when the CLI is unavailable. Affected merge requests show a hold with a setup and resume action. Manual publication and other GitLab actions that do not require an agent remain available.

When a usage-limit hold includes a reset deadline, MergeTether checks the CLI one minute after the deadline, independently of GitLab polling. Codex uses an account status request and Claude uses a minimal prompt with tools and session persistence disabled. A confirmed recovery wakes eligible work through the existing queue and retry policies. Unsuccessful checks back off from one minute to one hour. A newly reported reset can move the next check later. After three unsuccessful hourly checks, the banner explains why checks stopped and offers **Retry queued work**. An unsuccessful manual check leaves the automatic checks stopped. The schedule and its exhaustion survive restart. Holds without a usable reset deadline can be retried manually.

Codex reviews, feedback fixes, pipeline fixes, conflict work and reply corrections use the configured coding model and reasoning setting. Claude full tasks use the model configured in Claude CLI. The lightweight re-review readiness assessment has its own model setting.

The optional starting folder applies to manually opened CLI sessions. Desktop destinations receive the MR prompt without a starting folder. Automated workers start in separate per-run directories and are instructed to keep clones and worktrees there. They have full read, write, command and network access, without a CLI filesystem sandbox or interactive approval prompts. The additional project-task setting controls which configured tasks may run; it does not grant or restrict the worker’s tools.

Full tool access does not change the task’s GitLab authorization. Publication, approval, merge, thread resolution, author-follow-up push and conflict push keep their separate instructions and live app/helper checks. Executable work retains concrete failure diagnostics. Purely read-only assessment failures receive bounded automatic retries (three attempts with two- and eight-second backoff); after exhaustion, a fifteen-minute cooldown prevents repeated polling from restarting the budget immediately. Author-feedback assessment owns that budget end to end: each attempt makes at most one provider call, including through the app’s shared verifier wiring. The cooldown remains bound to the same account, configuration, MR evidence and reviewer-participation preferences; ordinary refreshes do not reopen it. Standalone re-review verification retains its separate two-attempt provider limit. A later poll can recover without requiring a manual MR action. Remote actions and semantic verdicts are not replayed by these retries. The separate lightweight re-review verifier has full CLI tool access with a read-only task: it can fetch live MR evidence through `glab`, but does not publish, resolve, push or merge. The app performs those actions under their configured policies.

Eligible failed or interrupted executable tasks receive up to three fresh automatic runs after 15 seconds, one minute and five minutes. The retry lineage and spent attempts survive app restarts and provider/profile changes. Startup, CLI recovery, policy changes and completed refreshes reconsider pending work. A missing permission or unavailable selected CLI pauses admission without spending a launch. Every admission checks the current account, MR, source head, workflow permissions and existing work; a closed MR or superseded/passed pipeline retires obsolete work. Each fresh worker reconciles prior commits, pushes, drafts and replies instead of repeating recorded commands. History records scheduled, started, failed and exhausted retries.

An MR's existing exclusive pipeline reservation pauses automatic retries without spending an attempt. Startup can reclaim the exact app-owned reservation of a queued, never-started run after repeatedly confirming its bound app owner is dead; the immutable pipeline receipt stays. Force Quit can leave a running CLI child alive after the app exits. Interrupted running jobs and legacy records without a durable never-started proof retain their reservation until live orphan ownership is reconciled. Retry history explains this pause. Confirmed pre-child contention, revoked permissions and CLI/account holds defer admission; an unknown failure or a recorded replacement retains the attempt.

Retries keep the originating workflow rule independently of display-history retention; turning that rule off pauses its pending retries. Unknown legacy task origins remain held until their authority can be established. Local-only conflict retries retain the existing no-push permission and stop when fresh evidence shows the conflict is gone.

A settings-policy cancellation can resume once the current policy permits it. Explicit **Stop** remains stopped across app restarts and model/profile changes; only a new explicit retry supersedes that decision. Semantic blockers and missing human decisions still require their corresponding resolution. Author-feedback continuation and reply repair use their existing source-bound assessment paths rather than the general retry loop. Reply repairs require an assessment begun after the preceding stop, preserve the exact account/source/draft boundary and retain their two-attempt budget across coding-policy changes. Publication-policy changes recheck pending replies, including newly eligible bot replies, without resetting exhausted repair budgets or publishing unsupported claims.

Failed merge-train pipelines can enter the ordinary pipeline-repair workflow when their content matches the current canonical merge result. The app verifies the current source and target commits, merge-ref parents, a completed comparison with no content differences, pipeline ownership and fresh MR/account state. This exception does not treat a successful train pipeline as proof of merge readiness.

These task permissions are not an operating-system or credential sandbox. Workers retain the signed-in account's tools and credentials, so app-side checks do not technically mediate arbitrary direct commands issued by a worker. Authenticated evidence detects substituted app records; it does not prove the semantic correctness of a review or defend against arbitrary same-user execution.

MergeTether narrows ambient authority without removing tools. Runs without a checked push permission (anything other than an enabled author follow-up push or conflict push) receive Git configuration in their environment that rewrites HTTPS, SSH and `git@` push URLs to an unsupported scheme, so an ordinary `git push` fails; fetches and local or `file://` remotes are unchanged. Lightweight verifiers, classifiers and draft generators also run without the forwarded SSH agent and read GitLab through `glab`. Workers are told never to read or send credentials. These are guardrails, not isolation: a worker can still read the user's glab configuration and on-disk keys, override its environment, or call the GitLab API directly with the signed-in token.

For executable MR jobs, MergeTether compares the current source head, public discussions and approvals around the worker process. An unattended worker requires a pre-launch snapshot. When a post-run read fails, MergeTether retries the read and holds automatic actions for that MR while waiting for evidence. Further refreshes retry the comparison, including after a restart. A clean result lifts the hold and restores a saved outcome. Changes outside the run's permissions pause automation on that MR until you resume it from the MR controls. Other MRs keep their configured automation.

When the source head moves during a run without push permission, history records both commits and when they were observed. A GitLab project push event can identify the account when it matches the source branch, both commits and the observation window. A verified push by another account makes the old run stale. An eligible automatic review can then start on the new head under its current review rule. An unknown actor or a push by your own account still requires resuming the affected MR, since your account can make changes by hand or through a worker. Other unexpected effects retain their own hold. A user-started run keeps its outcome if the audit evidence is unavailable. Stopped and cancelled runs are outside this comparison. The audit covers the MR's own source head, the account's published notes, its resolutions and its approval.

Provider configuration is currently explicit but different. Codex tasks ignore user `config.toml` and execution-policy `.rules` files and disable the app/plugin/memory integrations named in their invocation. `--ignore-rules` is not a promise that Markdown instructions or manually loaded skills are ignored. Claude coding tasks retain their normal settings sources, while supplying app settings and an empty strict MCP configuration; read-only verifiers explicitly suppress settings sources. Applicable skills remain part of the instructed workflow. Changing personal hooks or skill loading is a separate execution-policy decision.

**Settings → Agent → Agent settings → Agent task time limit** sets the coding-task deadline. The default remains 30 minutes; valid limits are 1–1440 minutes. Overrides select an already known repository by path and host, while matching its exact host and project identity internally. Add an MR to the board or Scope before configuring an unknown repository. The limit is captured from the run's saved configuration for both providers; changing automation settings keeps the existing cancellation/retry behavior and does not silently extend or restart a running task. Verifier and GitLab request timeouts are separate.

MergeTether refreshes GitLab when the Mac wakes. A wake during an active refresh queues one follow-up for that refresh. The inbox retains its latest confirmed state if GitLab is temporarily unavailable. **Settings → Agent → Agent settings → Keep Mac awake during agent tasks on external power** is on by default and saves independently of the automation profile. While the Mac is plugged in and an agent command is running, the app prevents idle system sleep and lets the display sleep. The assertion ends when the last command finishes, when power changes to battery, or when you turn off the option.

The same bounded read recovery applies before automatic approval and workflow admission. A failed preflight read does not mean a remote operation failed. After an uncertain approval response, the app reads the current approval state before deciding whether the operation succeeded; it does not automatically repeat an unconfirmed submission. Validated semantic assessments are persisted before final reads and reused after transport failures or a restart. These pending assessments authorize no publication until fresh source, identity and content checks finish. Automatic publication also waits for queued or running work on the same account and MR to finish; independent valid reply evidence remains available.

When an assigned check needs an installed, configured local runtime that is stopped, workers may start it through its service CLI and verify readiness before reporting a blocker. For an active OrbStack Docker context, they check `orbctl status` and `docker info`, bound startup to 60 seconds, then reconcile local Git state before retrying the failed check once. They do not install tools, change global runtime versions or Docker contexts, edit global hooks, relax checks, reset services, or replay remote writes. Coding-agent GUI integration remains outside the headless task.

### Full review

Choose **Full review** in the MR card menu on Mac to review the entire current change. It uses the selected Codex or Claude CLI and your existing GitLab sign-in. MergeTether supplies the same `mergetether` tool to either provider. The tool exposes `--help`, `context`, `diff`, `discussions`, `file show`, `work-item show` and `change show`. Repository files are read at the source commit under review. Work items and other changes can be read in the current project and other active repositories configured in Scope on the same GitLab host.

The provider receives only the review tool for those queries. GitLab credentials stay with the app-side adapter for these calls. The provider CLI itself still runs under your Mac account with its normal sign-in. A blocked tool or changed review context can stop the review. Each response has a 512 KiB limit, and a session accepts up to 128 reads.

The agent returns draft proposals. MergeTether checks the live account, merge request, discussions and private drafts before saving them. This pilot produces private Draft Notes and does not issue an approval verdict. It stays opt-in while the existing manual and automatic review paths remain available.

## Agent usage estimates

Under **Settings → Agent**, the **Agent usage** section compares work started by MergeTether through Codex CLI and Claude CLI. Overall and role cards separate coding-agent work (reviews, follow-ups, conflicts and pipeline fixes) from lightweight verification and classification, with reported input/cached/output tokens and unknown or partial runs. Choose Today, 7 days, 30 days, the current month or all tracked time. Provider bars can group by hour, day, ISO week or month; hover for the bucket's estimate and separate Codex/Claude amounts. The graph shows at most the latest 1,000 buckets and marks truncation; summary totals still cover the entire selected range.

Runs belong to their start hour in UTC, and ISO weeks begin on Monday. Daily history and the known-estimate average include zero-activity UTC days between the first tracked day or range start and the current day; a partial current day counts once. Unknown-only usage has no invented zero-dollar average. Tracking begins with the first new app-owned CLI run; earlier work is not backfilled. Counts, pricing versions and optional account/MR identity, title and URL are saved locally across restarts without prompts or transcripts. Unattributed older records remain in overall totals without being assigned retrospectively. Recent completion receipts are deduplicated; older finished receipts become hourly role/provider/MR totals, preserving all chart granularities. The top-five MR ranking follows the chart’s selected range and current UTC-hour cutoff; MR Details sums all tracked time for that exact host, account, project and MR, independently of the Settings date filter. Its verifier and reviewer / work agent rows show separate costs, reported tokens and **Agent requests**. The work agent includes reviews, author-feedback work, follow-ups, conflicts and pipeline fixes; the verifier includes evidence checks, reply verification and classification. Each app-started CLI invocation with a prompt counts as one request, even when it fails or its usage is missing. A fresh retry counts separately; repeated completion callbacks and cached checks do not add a request. Internal model turns, tool calls and separately opened MR conversations are not counted. No history is inferred for older runs without MR attribution.

Dollar amounts are comparison estimates, not subscription payments or billing receipts. Claude supplies its own [client-side CLI estimate](https://code.claude.com/docs/en/headless). Codex uses reported completed-turn tokens and the [published standard short-context API rates](https://developers.openai.com/api/docs/pricing), captured on 26 November 2026 for the exact supported model IDs. Cached input is already included in input, and reasoning tokens are already included in output. The Codex baseline excludes cache-write premiums, tools, long-context and service-tier adjustments; unknown model rates remain unavailable. Stored dollar estimates retain their original pricing version when app rates change.

Failed CLI exits still contribute reported usage. Failed Codex runs, timeouts, cancellations and interrupted runs retain available partial usage and an unknown/partial count; missing usage never implies zero. A final Claude cost envelope can still report its failed run's estimate. Unrepresentable aggregate totals are marked unavailable. Separately launched nested CLIs may not be included in their parent's reported usage. An accounting read or write error does not stop MR automation; Settings reports unavailable history while keeping any previously loaded totals visible.

New verifier receipts record their purpose, such as draft-proof recovery or re-review readiness, and an app-side run or attempt identifier when available. MR Details shows recent verifier requests and the total by purpose. After compaction, hourly totals keep the purpose and estimate diagnostics. The usage view distinguishes a partial estimate, missing provider usage and reported tokens for an unpriced model.

## Informational review acknowledgements

On your managed MRs, the accepted-feedback resolution setting also permits a thumbs-up reaction and closure of a purely informational thread. The current verifier must explicitly confirm that the entire thread, including author replies, has no question, requested change, expected answer, outstanding condition or ambiguity. An old or merely informational assessment is insufficient. Mixed threads retain the existing feedback and consent rules; acknowledging a pure thread does not approve a reviewer or accept their other findings.

Courtesy reactions also depend on account metadata and the comment's purpose. Regular human accounts may receive a thumbs-up on safe review feedback or a summary even when AI helped write it. Verified bot or service accounts receive one only for specific, concrete code-review feedback, not generic review summaries, no-findings reports or general observations about code structure. Explicitly generated generic workflow reports and artifact-generation status announcements are skipped even when their posting account has GitLab's regular account type. AI-like writing alone does not identify a bot or an automated workflow. Missing account evidence or a missing, unrelated or unclear purpose skips the optional reaction. These restrictions do not prevent an independently verified safe thread from closing.

The app checks its current account, MR head, discussion text, readiness, drafts and policy before each write. It checks existing reactions first and confirms new ones by reading GitLab again. Draft MRs follow the effective automation policy, and pending private replies retain their existing read-only restrictions. No courtesy text reply or private draft is created. Reactions and thread closure run through the app; headless workers keep their assigned task permissions even when a personal MR instruction allows these acknowledgements outside the app.

A failed optional reaction does not block independent corrections or an otherwise permitted thread closure. If GitLab does not confirm closure and the thread remains open, the MR offers a fresh verification rather than silently repeating the write. A new commit or a change in another thread does not replay that failed operation; a deliberate recheck or a change in the affected thread permits a fresh attempt. Resolved history is skipped, and acknowledgement work is limited to four new threads per pass.

## Task history, failure and migration

On Mac, **Event log** sits above **Details**, with **Agent usage** in its own section. The log shows GitLab comments, system notes, state, label and milestone changes alongside MergeTether worker runs, workflow events and application actions. Rows show the newest activity first, with badges for **GitLab**, **MergeTether** and confirmed **Automated** actions. Expand a row to jump to its discussion, read the exact timestamp and diagnostics, or open a linked run. When a GitLab result can be matched to a recorded app action, a single row carries the MergeTether badge. Otherwise both available records remain visible. Application events are bounded to 100 per MR and 1,000 total and scoped to the signed-in account.

On Mac, open **Window → Automation Activity** to troubleshoot agent runs and workflow events across merge requests for the signed-in account, including saved history for MRs that have left the board.

A feedback follow-up that finds no remaining work can complete without creating duplicate replies only after an independent, current-content assessment verifies the selected notes and required published responses. While a verification of the exact current content is running, the follow-up stays neutral. Its completion immediately reconciles the intent without waiting for a global refresh. Older observations cannot overwrite a replacement attempt. This does not waive the proof required to publish new drafts.

MergeTether persists task instructions and execution state locally, including output and errors. Isolated working files are kept under the app’s local `Assistant Runs` directory and can be revealed from the run, so interrupted or local-only fixes remain inspectable. Concurrent work for the same MR is coordinated. Before ordinary MR work starts, the worker verifies the queued GitLab account and live MR state. Closed or merged MRs do not start review/fix work; failed state checks do not become false completions.

Failed, cancelled and interrupted work stays inspectable. A deliberate retry creates another execution attempt; restarting the app does not silently replay a task that may already have changed GitLab. If a retry is needed, inspect any remote effects first.

Before starting a worker, MergeTether checks the Mac volume that holds its workspace. The threshold is the greater of 1 GB and twice the estimated source repository size. When the server cannot supply a repository size, the threshold is 1 GB. Running jobs reserve space until they finish and their generated files have been reclaimed. A job waiting for space is checked again after a worker releases its reservation. If no worker is running and the threshold cannot be met, the run asks you to free up space on the Mac and retry. Paired phones display the Mac's status.

During a run, MergeTether stops the worker if its workspace, temporary directory or output directory disappears or is replaced. A missing Codex result also fails the run. MergeTether checks current GitLab state before allowing a retry of interrupted work with possible remote effects. If the required pre-run evidence is missing, the run remains held for reconciliation.

Persistent worker output is capped at 16 MiB for stdout and 1 MiB for stderr. MergeTether keeps draining the streams after the cap is reached. A capped stdout stream fails the run because it may have lost part of the structured result.

Before retrying a pipeline task, the app reads its current MR and pipeline. A passed, replaced or currently running pipeline does not start another repair worker. Current evidence removes only the obsolete pipeline blocker from the board; the original run stays in history, and unrelated feedback or drafts keep their own actions. Missing or inconsistent evidence does not silently retire a failure.

MR menus and Details offer **Refresh from GitLab**. This refreshes tracked data through the normal monitoring path without clearing verification results or retry fences. Details share the card's MR actions and pin control. Automatic monitoring follows the selected refresh interval, with an hourly option available; forced refresh does not add a second periodic timer.

### Local retention after an MR finishes

MergeTether groups MR settings and journals by GitLab host, project ID and MR number. Each entry keeps its original account binding. Explicit settings saves also write the older keys so older installations still have the preferences and safety receipts they use. On upgrade, the app reconciles changes made by an older installation and preserves unreadable journals for diagnosis. Successful transcripts are stored once in the compatible run history payload, which is rewritten when the run history changes.

Retirement requires a successful single-MR read that confirms the terminal state and a matching authenticated account. An omitted row, partial response, failed read or older observation cannot trigger retirement.

| Data | Retention |
| --- | --- |
| Automation choices and write safety records | Kept across close, reopen and merge. A closed MR can reopen on the same commit at any time, so age alone never expires a safety record or automation opt-out. |
| Hidden review assignments | Kept across close, reopen, merge and restart while you remain assigned as reviewer. A confirmed unassignment clears the hide. |
| Board pin | Kept while open and for at least 30 days after close. A fresh terminal read can remove a pin once that interval elapses or when the MR is merged. |
| New-review marker | Removed on confirmed close or merge. The separate hold that pauses automation stays in place. |
| Worker history | On merge, or on a fresh read after 30 days closed, keep the newest 12 ordinary successful transcripts and the newest 12 eligible read-only reviews per MR and account. Active or queued runs, runs linked to receipts or other records, and runs with pending audits or recorded effects are exempt. Keep records that own a workspace, along with failed and interrupted diagnostics and worker checkpoints. |
| File evidence | A confirmed merge can retire display provenance and the cached author-feedback assessment. A close keeps them for reopening. Sealed verdicts, publication and draft proof, follow-up receipts and pipeline reservations keep their existing storage rules. |
| Worker files | Successful runs reclaim recognized generated build files. After an authenticated read confirms that the MR is closed or merged, MergeTether also removes clean, reproducible app-owned clones and eligible linked worktrees, and keeps the last 128 KiB of raw logs older than seven days. Active or recoverable work, local-only files and commits, checkpoints and saved evidence are protected. |

The app bundles `evidence.py` and `author_follow_up.py` under `Contents/Resources/Automation`. Workers use these helpers to read GitLab state and store local evidence.

An unanswered thread remains visible as needing a reply and cannot be automatically resolved merely because its reviewer approved.

Events that cannot be classified safely remain in **Inbox** for manual reading; they are never acknowledged as understood. Marking a routed event read does not prove a review finished, a fix was pushed or a draft can be published. Those outcomes keep their separate execution and remote-evidence checks.

Choose a profile in **Settings → Automation → Profile & permissions**, then adjust individual permissions. Until automation is explicitly enabled, automatic GitLab writes and worker push or thread-resolution permissions remain off. Missing consent in older settings stays undecided regardless of saved feature flags. Running a review manually permits that review and private drafts; it does not enable later automatic approval, publication, merge, resolution, reactions, to-do acknowledgements or re-review requests. Explicit manual GitLab actions remain available. The page groups preparation, comment publication, delivery and completion. **Review & feedback** retains the trigger and repository rules; **MR Events** retains its event filters. **Advanced** keeps saved shell titles and commands, with their stored enabled/disabled state visible; they do not run automatically. Choosing a profile or migrating a legacy handler to the coding agent remains explicit. The app preserves existing settings across upgrades. Onboarding starts with **Manual** when no agent is selected. Choose a signed-in agent to enable the automation profiles during setup.

| Profile | Automatic preparation | Publication and delivery |
| --- | --- | --- |
| **Manual** | Automatic task rules and verification are off. | Start tasks and GitLab actions yourself. Explicit **Run review** and manual GitLab actions remain available. |

Manual and Max have compact summaries; Safe and Trusted list both automatic work and the actions left to you. A matching profile is recognized from the current permissions, independently of the last selected defaults used by reset buttons. Hand-editing the controls to reproduce a preset selects that preset automatically. Saved settings record the currently matching preset independently of the reset-button baseline. On an upgrade, a missing permission uses that active preset's default; customized configurations keep the conservative default. Explicit saved values are retained. Legacy settings infer a matching preset from their existing permissions before adopting the new default. New profile-managed settings must use this migration path and join profile matching and custom-profile snapshots.

**Custom** becomes available after you create a nonmatching configuration. The form retains your latest custom permissions when you try another preset; an explicit save retains that choice across restarts. Choosing a preset does not erase the saved custom configuration. Fresh installations with no custom configuration do not offer an empty Custom option. Older saved **With checkpoints** settings retain their permissions; they never acquire Trusted permissions on decode or upgrade.

Global permissions, automatic review and feedback handling, verification, event modes and CI retry permissions are editable on **Profile & permissions**. **Settings → Agent → Agent settings** contains provider-specific models and reasoning options; **Review & feedback** retains handler details and repository restrictions; **MR Events** retains event filters and timing. These pages do not contain a second copy of the global permission switches.

Safe has an independent public-action boundary. Private drafts and local preparation can continue, but enabling an individual delivery switch does not bypass that boundary. Explicit manual actions remain available. With follow-up push disabled, local code proposals remain in the task result rather than creating completion replies that imply a delivered fix.

A successful settings write is reported separately from a safety-data hold. Corrupt receipts can keep automatic actions paused even after new settings and Custom history are saved successfully. Failure to remember optional Custom history leaves the previous snapshot available and does not itself change active permissions.

Waiting for review never creates a comment or a draft. After the configured waiting period, the rule can track a local event or stay off. Older settings that ran an agent for this event are migrated to local tracking; queued reminder jobs are retired.

**All eligible comments** is the default publication mode in Max. It bypasses optional publication filters. Trusted uses **Replies to AI or bot feedback**; Safe and Manual use **Private drafts only**. Conditional publication also applies the selected repository and author conditions; nonmatching comments remain drafts. Checked-content, account and remote-evidence checks still apply in every automatic publication mode. Existing saved custom choices are preserved. **Allow replies to bot accounts** is a separate publication permission, enabled by Trusted and Max. In conditional modes, a verified bot account (including a local stable-ID bot declaration) can qualify instead of an AI authorship assessment; repository and author filters still apply. All eligible comments already includes bot replies.

Automatic re-review in Trusted can continue after you deliver fixes or publish the pending replies. Local preparation is not evidence that a proposal reached the remote branch.

Configure these in **Settings → Automation → MR Events**. Choose **Off**, **Log a preview**, **Track event** or **Run with agent CLI** for each rule. ## The human checkpoint

**Settings → Automation → Profile & permissions** contains the **Comment publication** selector plus separate approval, push and thread-resolution permissions.

- **All eligible comments** is selected by Max. In this mode, the app waits until drafts stop changing across two refreshes and verifies current evidence before sending them. GitLab cannot identify which agent created a draft, so this can include your own pending drafts on MRs the agent worked on.
- **Replies to AI or bot feedback** limits automatic publication to eligible replies to content written or substantially assisted by AI, including comments posted from a person’s account. An account name alone neither qualifies nor excludes a source. Verified GitLab Duo comments qualify directly; other sources require a high-confidence assessment tied to the source note ID and exact body hash. This is a probabilistic judgment based on text and discussion context. Missing assessments mean unclassified, rather than human-authored. Likely manual, unassessed and uncertain sources keep their replies private. Edited comments and later follow-ups require their own assessments.
- **Private drafts only** leaves comments private until you explicitly publish them.
- Automatic publication rejects slash-command lines and `resolve_discussion`. It publishes checked draft IDs individually, after another read. Unrelated or changed drafts remain private.
- **Review and confirm** on an MR card opens its discussions and draft preview. Checkboxes select exact draft versions for **Publish selected**; **Publish all comments** remains available. Selection starts empty, never includes newly arriving drafts, and is cleared for edited or removed drafts. The selected action stays available at the bottom while browsing long threads. Only selected IDs are published, individually, after current-account and body checks. Changes to unrelated drafts do not enlarge the selected set. These explicit manual actions work without the agent CLI or automation and bypass automatic publication filters. Explicit publication sends the previewed set only if it is unchanged. Publishing in GitLab is also supported; the board refreshes pending confirmations while it is open.

When an AI condition applies, the configured lightweight verification model proactively assesses current source comments that lack a matching result, including while reply drafts or remote verification are pending. It considers text and discussion context, regardless of the posting account, and treats comment instructions as untrusted data. Only a high-confidence AI-assisted assessment can qualify a source; likely manual or uncertain results leave its replies private. Oversized or unavailable text remains uncertain. The app re-fetches current source bodies before saving assessments and reuses unchanged results. Failed and uncertain checks are cached by source body, provider, model, reasoning setting and criteria version to avoid repeating them on every refresh. Assessment does not publish anything or relax scope, draft-content or remote-evidence checks.

The content heuristic combines precise references across code locations or detailed implementation-to-test reasoning with consistent code quoting, author-written line references, polished language and repeated review structure. Em dashes, sentence-ending periods and other punctuation are weak supporting cues and never sufficient alone. Repository knowledge is not evidence of manual authorship. Multiple corroborating signals without meaningful counterevidence can support `ai_assisted` at `high`; `very_high` is also accepted. A likely manual or uncertain classification never qualifies, regardless of its confidence label. Automatic diff anchors are not author-written line references. These are workflow heuristics, not verified authorship or universal probabilities.

Assessments record their criteria version. After a criteria change, older nonqualifying results are assessed again once under the current provider/model/reasoning setting; unchanged current results remain cached. Current qualifying content-bound evidence is retained. This does not change publication mode, scope, remote-fix proofs or other publication checks.

Under **Settings → Automation → Advanced → AI comment assessment prompt**, edit the criteria for both comment badges and the AI condition for reply publication. Select **Restore Default Prompt** and then **Apply Changes** to return to the built-in criteria. A blank prompt also uses the built-in criteria. Assessments are reused only for the matching prompt. Bot identity checks, built-in attribution parsing and other publication requirements still apply.

### Optional publication conditions

Expand **Publication filters** in Profile & permissions to restrict repositories, MR authors, source-comment authors or require verified/high-confidence AI-assisted feedback. **All eligible comments** ignores these filters. In conditional modes, all active conditions must match (AND). Within an author or repository list, any selected identity qualifies; an empty list adds no restriction. Explicit manual **Publish all** bypasses automation filters. Active scope and the other execution and publication checks still apply to automatic actions.

Repository and user entries are verified through GitLab and stored as host plus stable project/user IDs; their labels are display text. Source-comment conditions check every external comment in the latest incoming exchange: comments after your last reply before the newest incoming comment. Your later replies do not erase those sources. An unknown author, missing discussion evidence or a nonqualifying follow-up keeps the response private. A new finding without a source comment cannot satisfy source-author or AI conditions. AI assessments remain bound to the current source note and exact body.

The board’s automatic-publication preview and the last live check use the same policy. Changing the mode or any condition invalidates the old preview immediately. Publication still uses exact checked draft IDs and all existing draft-content, remote-proof and account checks.

Reset arrows beside the publication mode and checkpoint permissions restore only that setting using the profile you last explicitly chose. For legacy or custom settings without a known profile, the reset menu lets you choose **Manual**, **Safe**, **Trusted** or **Max** defaults for that setting. Resetting one condition restores only that condition; **Reset publication filters** restores the selected profile’s filter defaults. Other permissions, scope, agent choice, custom task instructions and drafts remain as configured. **Apply Changes** saves the policy and immediately starts a fresh MR check; publication follows when the current evidence passes. These conditions apply only to automation: an explicit manual **Publish all** action ignores them.

Draft readiness requires a check covering the current MR head and discussion content. New or edited comments invalidate it; resolution-only changes preserve it. Failed or missing checks leave the drafts visible with an explanation that they need review. Explicit manual publication remains available from the MR details.

## Remote proof for author follow-ups

When the verifier confirms that a single addressed finding only needs a standard acknowledgement, MergeTether prepares that reply directly in the review thread. The reply contains the verified disposition and a thank-you. The app binds the draft to the current account, branch head, discussion and exact body. Publication still follows the selected policy and checks current GitLab evidence before sending. A reply that needs technical details or test claims follows the coding-agent and independent verification workflow.

After automatic publication, MergeTether can reuse the current feedback assessment when GitLab shows the exact verified reply as the sole discussion change and the MR evidence still matches. Re-review waits for an author-feedback assessment already running for the same evidence. A failed or cancelled assessment releases that wait.

Known app-origin sealed drafts with incomplete older proof can receive one fresh verification per exact account, MR, draft, discussion, code and verification context. Current automation permissions must still allow it. The lightweight verifier reads live GitLab evidence and checks each draft's claims. It archives independent current proof without changing the original run's result. Each requested draft subset remains bound to its complete historical origin. Verified replies can publish individually while uncertain siblings stay private; refreshing one draft does not adopt or invalidate its unchanged siblings. Unknown origins, edited drafts and uncertain claims remain private. Verification progress is neutral; a failed check shows its reason and a retry action.

A required file missing at the verified commit leaves the affected proof blocked until its evidence changes or you choose **Verify drafts again**. Other eligible draft origins can still be verified. Transient GitLab reads retry independently and back off after repeated failures. A successful verifier response is saved before the final evidence read so that a later read retry can reuse it.

An unrelated follow-up waiting on external evidence does not erase a prepared reply’s known origin or strand its interrupted repair. Current claim verification is separate from task completion. New writing work requires fresh verification before an older cached result can authorize publication; active or unconfirmed ordinary writing work pauses that check. A change during repair admission returns an unused reservation when no worker started. Historical task outcomes, explicit Stop and the repair-attempt limit remain intact.

Rejected checks remain fenced per exact draft across restarts and narrower batches. Publishing a verified sibling or automatically tracking another MR does not reset that result. Meaningful new claim evidence, such as changed code, discussions or CI, can permit a fresh check; **Verify drafts again** explicitly resets the attempt fence while retaining valid proof.

Verification thinking applies to new model invocations. Changing it does not discard a completed draft-claim verdict, including one awaiting final live checks after an I/O failure. Current evidence and permissions are rechecked before using that verdict. Use **Verify drafts again** to request a new assessment of unchanged claims.

Workers receive a private temporary directory in `TMPDIR`, `TMP` and `TEMP`, and an explicit JVM `java.io.tmpdir` option. A blocked author follow-up with an identified local temporary-file permission failure can receive one fresh automatic attempt while its original commit, account, discussion and active permissions still match. The attempt is persisted before launch and reconciles existing remote changes before doing new work. It preserves the old failure in history; failed, cancelled, interrupted or otherwise uncertain runs are not blindly replayed.

A failed, cancelled or interrupted feedback follow-up can also be reconciled without starting another worker. The current verifier must prove that every assigned note is addressed or informational and any required reply is already published, after fresh account, source, MR context, discussion and draft reads. That proof belongs to the exact stopped attempt and current conversation. It retires the obsolete retry prompt across the board and inbox and releases the historical unfinished-work gate; current feedback, unpublished replies and every approval, CI and merge check still apply. Original execution results remain in history. Reviews, conflict tasks and pipeline reservations keep their separate recovery rules.

A blocked feedback follow-up needs stricter proof: the verifier receives the exact latest eligible run, its selected feedback and actual stopped step. It may retire that run's obsolete attention only after current evidence proves every selected correction or explanation complete, every owed reply published, and the stopped step no longer blocking the assigned MR task. Missing proof, changed run context, unverified required tools or checks, and unrelated work keep the block. The proof binds the current account, commit, MR context and discussions and changes no execution history. It removes only the obsolete stopped-work gate: configured automatic merge may continue when every ordinary approval, pipeline, scope, Draft, commit and discussion check passes. It grants no independent approval, merge or deployment permission.

**Let the agent push fixes to my merge requests** is enabled by Trusted and Max and is independent of conflict-push permission. Turning it off is preserved across restarts. Installed MR skills can refine the work, but are not required for this sequence.

An attempted feedback run does not mean its work finished. After a failure or an interrupted run, a fresh feedback assessment can schedule one bounded reconciliation of the still-outstanding notes using the currently selected CLI, including after switching between Codex and Claude. The worker first checks remote changes, published replies and existing private drafts, then completes only the remaining corrections or replies. The recovery budget is saved per original run and comment across restarts; unchanged polling cannot repeatedly retry it. A cancelled run stays stopped unless the selected CLI changed. Blocked runs retain their explicit decision gate.

This uses the verified-feedback path and its persisted recovery receipts. Clearing general event deduplication would replay unrelated events; resubmitting the old command would reuse stale permissions and evidence. Fresh preparation preserves the current account, scope, source-head and discussion checks and keeps publication separate.

The worker runs the bundled `author_follow_up.py status` command at the start and immediately before pushing. Only an explicit author-follow-up run carries that permission; review, legacy and conflict tasks cannot inherit it. Before drafting it runs `author_follow_up.py verify` with the run ID, tested/pushed commit and an evidence file containing the assessed discussion fingerprint and SHA-256 hashes of committed source/test files. The verifier reads the authenticated user, owned MR, source branch and remote file contents.

Only after verification may the worker save/refetch reply drafts and bind their IDs and exact body hashes using `author_follow_up.py seal`. Preflight tokens are one-use. Sealed receipts are archived separately per verification, so a later task cannot replace proof for earlier unpublished replies. Publication rechecks each reply against its exact known origin, current source and draft body; newer unfinished work still blocks automatic publication. Known older sealed run artifacts can be recovered, while unknown or unsealed drafts remain private. Existing user-created or legacy drafts cannot be silently adopted. A previous sealed draft can be rebound after fresh verification when a later stacked fix changes the remote head. The bundled standalone `author_follow_up.py` helper supports this evidence flow without desktop setup.

Automatic publication rechecks the account, current run, push permission, source branch, remote head, file content, discussion fingerprint and draft body. Missing or stale evidence keeps replies private even under publish-all. Existing drafts are never deleted or rewritten by this gate. Worker-written preflight and seal files remain untrusted origin candidates. Successful fresh semantic recovery records are authenticated by the app using its protected completion-journal key; unsigned or modified assessment files cannot authorize automatic publication. Known legacy candidates may be reassessed, while old unauthenticated results need fresh verification. This detects later record substitution; it does not make a full-access worker or its chosen source-file claims inherently trustworthy.

When the source HEAD changes, known app-created reply drafts can receive a fresh, read-only claim assessment automatically. Their recorded IDs and body hashes are checked against the app-known run/account context, while source-file hashes and the assessment are collected again at the new HEAD. Only individually valid replies gain current proof; publication still applies the current AI, author and repository conditions. Uncertain or invalid claims and drafts outside those conditions stay private. Unknown or edited drafts are not adopted, and a second head or discussion change during verification invalidates that attempt. Rechecking does not rerun the coding worker or rewrite any draft.

The verifier proves the selected committed files reached the remote revision. Meaningful tests, sufficient file selection and claims matching the changes remain the worker’s responsibility. GitLab has no conditional draft-publication endpoint, so a small race window remains after the final check; checks are repeated immediately before sending.

## Re-review readiness

**Settings → Automation → Profile & permissions → Re-review verification** is on for Safe, Trusted and Max, and off for Manual unless explicitly changed. It uses an independent verification model: Luna for Codex and Haiku for Claude by default.

**Verification reasoning** is shared by Codex and Claude across feedback verification, draft-claim checks and AI-assistance assessments. It offers Low, Medium and High, with High as the default for new and existing settings. Explicit saved choices are retained, including when applying a profile. The reasoning choice is separate from the coding agent’s reasoning setting.

After changing the review or verifier prompt, schema, default model or reasoning, run the [model evaluations](model-evaluations.md) against synthetic merge requests. The offline tests capture the current requests and check the scoring rules. Live provider evaluation is opt-in.

The verifier receives the MR target, expected commit, source note IDs and semantic context, with bounded, credential-filtered title, description, diff and discussion evidence when available. It can use `glab` to read the current MR, paginated discussions, diffs and relevant files. Large inputs can use target metadata instead of failing only because inline evidence exceeds the limit. It classifies every external non-system comment, including general comments, and returns reasons tied to note IDs. Informational summaries require no answer. A concern blocks its reviewer; unrelated feedback need not block another reviewer whose concerns are addressed. Unsupported author claims are not proof, and missing evidence stays uncertain.

Once all current feedback is verified as addressed, informational or explicitly ignored, and all required replies are published, re-review also includes assigned human reviewers who participated earlier or whose approvals were reset. Re-review eligibility uses the current GitLab reviewer list and is checked again before sending. A participant who leaves that list receives no re-review request; adding them back restores normal eligibility under the existing readiness and exclusion rules. Re-review never adds an absent commenter to the reviewer list. It uses GitLab's re-request action rather than posting reminder comments. Current approvers, bots and inactive accounts are excluded; assigned people who have not participated receive no extra request. An outstanding or in-progress review is kept, and requests are deduplicated by source commit and reviewer activity across restarts. Earlier reviewers wait while any feedback remains blocking or uncertain; individually addressed reviewers retain their existing per-reviewer readiness checks.

After an unconfirmed request, a fresh GitLab `review_started` state for the same assigned reviewer, source commit and reviewer activity can confirm the recorded attempt without sending another request.

A reviewer’s explicit request to stop participating is assessed against an exact quote from their current comment. A pure opt-out needs no code change, reply, acknowledgement or reaction, and excludes that participant from re-review. Any genuine technical concern in the same comment still needs assessment and correction; an opt-out never supplies acceptance or permission to resolve a discussion.

**Settings → Automation → Advanced → No automatic replies or review requests** stores explicit exclusions by GitLab host, signed-in account and stable participant ID. These exclusions apply to automatic replies, acknowledgements, reactions and reviewer invitations, including final write checks and worker instructions. They can be reversed with **Allow again**. Changing them invalidates affected readiness evidence without changing the automation profile. Existing drafts and history remain intact; manual checked publication remains a separate user action.

The verifier correlates review summaries with the concrete findings they reference across discussions. A verified correction or substantive answer in the matching thread avoids a duplicate answer in the summary; distinct requests or remaining conditions still block readiness. Informational classification does not grant reviewer acceptance or consent to close referenced findings, and a summary awaiting reviewer reconsideration stays unsafe for informational closure.

A published reply in a resolved finding can also help verify a stopped follow-up that selected both the finding and the active overview from the same review. Reconciliation requires the original selected note text, live evidence that the assigned work and replies were delivered, and confirmation of the exact run. Task history keeps the original result.

Workers and verifiers distinguish an observed defect from a reviewer's proposed remedy. Rejecting an unsupported remedy does not settle an independently supported defect. The coding agent researches accessible contracts, related callers and tests, and can implement a warranted correction using established behavior without inventing an undocumented business meaning. A genuine external decision remains an explicit, concrete question after that evidence has been checked; routine research and code work stay with the configured agent.

A prerequisite for a later rollout, deployment or organizational step is not unfinished MR work merely because third-party confirmation is absent. A verified correction or supported explanation with the required published reply can wait for the reviewer without another worker or duplicate answer. Explicit requirements before merge, actual unresolved defects and decisions needed to perform the current assigned work remain blocking. Neither worker nor verifier may invent external acceptance. Assessment-policy changes and changed blocked-run context invalidate the corresponding session cache.

These assessments support re-review requests and the accepted-feedback checks below; they never themselves authorize a GitLab write. The output schema requires one result for each external comment ID in an active thread. The app independently rejects duplicates or missing evidence. Read-only evidence gathering uses up to three attempts with two- and eight-second backoff, followed by a fifteen-minute cooldown after exhaustion. Each verifier invocation can also retry failed or incomplete provider output once. These retries retain full read-only CLI tools and never replay an executable MR task or remote write. Results are reused for unchanged inputs during the app session and invalidated by account, head, discussion, provider, model or reasoning-setting changes. Exhausted failures remain visible, with a deliberate retry available; a later poll can retry after the cooldown.

Re-review uses a complete author-feedback assessment for the current MR evidence as soon as it becomes available. It replaces an earlier standalone result for that evidence. If a read or verification fails, the MR offers **Verify again** and can retry after the failure cooldown. When a specific concern remains, the MR links to its source comment. If no concrete feedback or draft blocker is known, **Confirm readiness and request re-review** allows explicit manual confirmation. That confirmation binds the displayed head and discussion content. The app rechecks the live account, scope, MR state and drafts before notifying reviewers. With automatic verification off, manual confirmation remains available when these checks permit it. Other agent automation requires a signed-in CLI.

## Accepted feedback on your own merge requests

**Settings → Automation → Profile & permissions → Resolve addressed feedback after reviewer acceptance** is enabled by Trusted and Max and disabled by Safe and Manual. Existing explicit settings are preserved until a profile or permission is changed. It applies only to your own open MRs within the effective automation policy, including explicitly enabled Drafts and requires the signed-in selected CLI.

This switch controls automatic thread resolution. Turning it off still permits semantic verification and configured author follow-ups; it does not remove the feedback check required for automatic merge.

The verifier checks the current MR title, description, diff and every external comment, including general comments and conditions in other threads. A reviewer's current approval is consent to close their verified addressed threads; it is never proof that their requests were fulfilled. An advance approval such as “approved, but still do X” remains blocked until the request is implemented or substantively answered with a justified explanation. Warranted work enters the configured author-follow-up workflow, with its existing push and publication permissions.

A later explicit acceptance comment by the same reviewer can also provide consent. It may be a general summary covering several findings. The verifier must tie it to the current code and concerns; the app checks the cited note's author and chronology. Generic thanks, another person's approval, stale acceptance and account-specific exceptions do not qualify. Every actionable participant in a thread must be satisfied, and missing evidence prevents resolution.

When a current, complete assessment confirms that your work and replies are finished, the app can show a reviewer wait for a remaining GitLab request for changes. If GitLab has moved the reviewers to pending or in-progress review, confirmed re-review records for the current commit and reviewer activity also establish that wait. GitLab's approval and merge restrictions still apply.

Before each resolution the app rechecks the live account, owned MR, source head, MR title and description, entire discussion text, current approvals, drafts, settings and scope. Pending replies must be published first. The MR detail shows remaining corrections or explanations, unpublished replies, verification failures and reviewers whose acceptance is missing. A reviewer who has already accepted is not asked to review the same unchanged feedback again. Changes to the MR title or description invalidate semantic assessments even when the source commit and comments are unchanged.

Each automatic follow-up attempt records the reviewer note ID and content revision separately from visible job history. An agent reply, new commit or cleared history alone cannot replay that attempt; edited or new reviewer feedback can start new work, and explicit manual retries remain available. Large sets are handled in bounded batches. Stale live evidence triggers a fresh poll; actual verification/API failures remain visible for deliberate retry rather than automatically repeating uncertain remote work.

A successful follow-up also invalidates any semantic assessment made before that run completed. If a fresh assessment independently identifies concrete remaining author work or supplies a valid source-bound technical question, the app can schedule one scoped reconciliation per original run and reviewer-note revision. It requires current account, source, discussions, settings, scope and push permission. An unchanged source is bound to the original expected commit; delivered source changes require that run's matching remote-content proof. The successor receives the specific residual evidence and reconciles prior remote work before editing or drafting. Its durable budget survives restarts and cleared job history, and descendants inherit it. Generic uncertainty, missing replies, unavailable evidence, a newer failed attempt on that concern or an active worker cannot by themselves trigger this reconciliation; existing draft and publication checks still apply.

Private code questions stay separate from the source comment's assessed state. Each quotes exact source context and names a bounded technical question; an additional observation is never attributed to the original reviewer. Both the first worker and a permitted scoped reconciliation receive the verifier's question and original assessment. The existing **Handle feedback on my merge requests** option (or an enabled matching discussion workflow) controls automatic handling; when it is off, the existing manual checkpoint remains and no extra reviewer session is started automatically. Codex uses the configured coding model/thinking, and Claude uses its CLI model configuration. No extra reviewer process or permission setting is introduced.

The reviewer/fixer must confirm or disprove each hypothesis with current code evidence, then fix only a meaningful in-scope defect under the ordinary ownership, scope and push rules. It records the disposition separately in its task result; it does not create a new discussion or reply solely for an additional private observation. With push off, pending or failed, proposals remain in that result. Its completed report returns as supplementary evidence to the final verifier, which still checks live source and required author replies. A pending private code question holds automatic readiness independently of an already addressed source comment; failed or blocked work keeps its existing gates. Rewording a question or polling/restarting does not renew the original note's reconciliation budget. A deliberate manual run retains the existing retry behavior.

**Merge when ready** waits until every explicit GitLab dependency is **merged**. Open, Draft, locked and closed-without-merging dependencies keep it on hold. A branch-stack parent also blocks a child, regardless of the parent's author. Missing, hidden, failed, stale, incomplete or ambiguous dependency/stack evidence never authorizes an automatic merge. The same dependency checks run during polling and when the MR's auto-merge setting enables a fresh check.

A child must not merge into its parent's branch. After the parent merges, a non-default target still matching that parent's source branch remains on hold, including after an app restart. MergeTether checks historical MRs for that target branch as well as the open stack. A reused branch with a historical MR is conservatively held for target review, even when it could be a legitimate release target. An ordinary non-stack release target with no matching MR remains eligible. Details explain the hold. The existing stack follow-up prepares a rebase/retarget plan; the user reviews and changes the remote target. Enabling automatic merge grants no retarget permission.

Readiness uses fresh dependency snapshots rather than the cached dependency row. Immediately before the merge write, MergeTether checks them again and verifies that the source and target context still match. GitLab's merge SHA condition protects the source; its API provides no atomic condition for dependency or target changes, so a small race remains after the final reads. Desktop and remote **Review merge** actions open the MR details. The explicit **Merge now** or **Set to auto-merge** action performs its own fresh preflight and confirmation independently of background automation.

Automatic merge also requires a fresh complete semantic assessment when external feedback exists. A remaining condition in a general comment blocks it even when GitLab's approval rules are satisfied and every resolvable thread is closed. Turning off thread resolution does not bypass this merge check.

Automatic merge checks whether the project requires resolved discussions at readiness and before submission. Cards and Details explain when this policy holds automatic merge. Automatic and manual submissions both check the MR's current approval rules and send the checked source SHA to GitLab. The project controls whether approvals carry over after a push.

### Explicit merge and GitLab queues

Manual merge is limited to your own open, Ready MRs with current GitLab merge permission. It uses the same source/target, dependency, draft, semantic feedback, published-reply and unfinished-work checks as automatic execution. Turning off global automation, pausing an MR or opting out of automatic merge does not remove this deliberate action. Automatic execution applies scope, project and per-action permissions.

Project metadata selects immediate merge or a merge queue. While a pipeline is active in an ordinary project, automatic merge waits in MergeTether. Once the pipeline succeeds, the next submission checks the current feedback and merge requirements. Use **Merge when ready** to explicitly delegate an ordinary merge while a known active pipeline runs. This requires GitLab 17.11+ and uses `PUT /merge` with `auto_merge=true`. Train projects use the SHA-bound [merge trains API](https://docs.gitlab.com/api/merge_trains/). Failed, manual and unknown pipeline states remain blockers. Missing capabilities never trigger a guessed fallback. An enqueue response is followed by a fresh MR/train read and is reported as queued or in train, never as a completed merge.

A persistent receipt is saved before submission. An ambiguous response, timeout or lost postcondition does not permit a blind replay, including after restart. Observed user-created queues are recorded separately, so their disappearance does not silently authorize an automatic replacement. The app never cancels or replaces queued work. A removed queue without verified failure evidence or a changed active queue gets an explicit GitLab checkpoint. Existing polling compares source, target, semantic/discussion content and automation settings against the receipt; changed evidence is shown for review. GitLab controls the delegated queue between refreshes. Its SHA precondition does not atomically bind future comments, target edits or app settings, and the app cannot guarantee cancellation when new feedback arrives or scope is disabled. Review such a queue in GitLab. Existing CI, conflict and feedback repair permissions remain separate; merge grants no retarget or push permission.

After a confirmed app-submitted merge train attempt fails CI, MergeTether can recheck a later source revision with a verified successful pipeline. It matches the server's admission and failure notes and the failed train pipeline to the saved attempt, and checks the source revisions in GitLab's diff history. The normal approval, discussion, dependency and automation checks run before a fresh SHA-bound submission. A new queue already started for the later revision is tracked as an observed queue.

Fast-forward trains can fail while replaying an intermediate commit even when the MR's final trees are mergeable and `has_conflicts` is false. MergeTether recognizes the latest GitLab system removal note only for the exact source, MR train ref and current target branch head. An active queue wins over historical failure evidence. A synthetic train base containing other MRs does not authorize repair against those branches. Missing target evidence holds readiness. Cards and Details link the specific train rebase failure; the separate conflict settings can prepare its resolution even when an earlier merge outcome remains uncertain. The worker must reproduce commit replay, then verify actual FF/train preparation on its proposed result before a permitted normal push and again from the verified remote source and current target afterwards. A clean final-tree merge is insufficient, and rewriting published history still requires explicit user authorization.

New train attempts save the last observed note ID before writing. A newer, exact-context rejection can be recorded as proof without deleting the attempt or replaying the same source. Only that proof plus a changed source head permits fresh merge checks after repair. Lost responses without rejection proof, legacy attempts without a note baseline, and unchanged source heads retain their conservative checkpoint.

## Feedback outcome and reply publication

It does not claim that every suggestion was implemented. A local commit, an unpushed fix, a private draft or a claim of completion does not prove an upstream correction.

The verifier records justified rejections separately from implemented corrections in its per-note evidence, while the thread keeps the aggregate **Feedback addressed** label. A later informational acknowledgement such as “super” does not invalidate that coverage. New or edited requests need a current assessment and their own verified answer; the last speaker or note timestamp alone cannot prove coverage. Empty, unavailable or unknown reply states stay hidden. These display rules do not satisfy any publication, resolution or merge prerequisite.

## Automatic approval

**Approve merge requests automatically** is enabled by Trusted and Max and disabled by Safe and Manual. It is off in new or recommended settings until you choose a delivering profile or turn it on. Set **Automatically approve when** in **Settings → Automation → Profile & permissions**. Changing presets keeps your selected threshold. Upgrades keep a saved permission and threshold; older settings without the permission inherit it only from an explicitly saved Trusted or Max profile.

| Threshold | Remaining issues allowed |
| --- | --- |
| **No major issues remain** (default) | Minor code suggestions and editorial feedback. |
| **No code-related issues remain** | Editorial feedback, such as wording in the MR description. |
| **No issues remain** | Approval requires no remaining issues. |

Each threshold considers active discussions from every participant, including general comments. Substantive issues, explicit approval requirements and unresolved uncertainty about major issues block automatic approval. A resolved thread and all its replies are excluded. Resolved discussions remain visible in GitLab. An existing private reply in a resolved thread stays private until you handle it.

When MergeTether automatically approves under a threshold that allows remaining findings, hover over or select the approvals badge on the card or in MR Details to see a note for the approved revision. The local automation event log retains that approval and links to the review run.

Automatic approval also has these requirements.

- A review verdict that meets the threshold and covers the current MR head, title, description and discussion content, bound to the authenticated account and a successful app-managed review.
- No pending drafts and a completed comment-review checkpoint when one is pending.
- An open MR you review, within the effective Draft and automation policy, which you have yet to approve.
- The selected CLI is ready for automation.
- The same target project, target branch and diff base the app captured during review, confirmed by its own live single-MR reads including the final check before approval. An earlier verdict without a recorded target requires a fresh review for automatic approval.

An MR with a qualifying review can receive automatic approval regardless of the presence or status of a pipeline and the number of changed files. Merge readiness follows its own rules.

Approval is pinned to the checked source SHA, target branch and diff base. Retargeting an MR or a new diff base without a new commit withholds automatic approval until a fresh review. If the MR’s review-update rule runs automatically, it can schedule a fresh review of the current diff. A new or edited comment invalidates the verdict; resolution-only changes preserve it. If GitLab refuses automatic approval, the app stops retrying that commit and retains the manual **Approve** action. Disable approval for an individual reviewed MR in its detail controls or automation scope settings. On someone else's MR, resolution remains limited to your own verified review findings; accepted-feedback resolution applies only when you own the MR.

To make your own decision, open the approvals badge on an MR you review and choose **Approve** or **Remove approval**. Manual approval uses the displayed revision and the signed-in GitLab account. Removing approval sets **Approval → Off** for that MR and shows a confirmation. The orange Mac bolt marks this customization. The setting persists across commits and restarts. Set **Approval** back to **Default** or **On** from the Mac bolt to resume automatic approval under the current rules. Manual approval and removal leave the MR’s other automation settings in place.

The reviewer checks factual claims against the current commit and full changed-file list, including generated or collapsed files. A wholly disproved GitLab Duo finding can be classified as having no remaining issue after the reviewer verifies the bot identity and the complete active thread. The worker leaves the thread open.

Publishing an unchanged draft captured in that authenticated review completion can preserve the verdict. The app confirms the exact newly published notes and unchanged existing discussion text before authenticating the resulting fingerprint. Later or edited drafts, direct comments and unsigned draft-history caches cannot extend automatic approval under an older review.

Old verdict files without an authenticated account or evidence of the reviewed title and description require a current app-managed review. An older objections verdict or unclassified active feedback requires a fresh review before the thresholds can apply. A verified GitLab Duo false positive from an authenticated earlier review can still qualify when the review covers the current title and description, and live bot identity and exact thread evidence match. This authenticates the origin of the review result. The app relies on the review worker's judgment for the findings themselves; the app verifies that the judgment still applies to the live diff. GitLab checks the source SHA at approval time. A target change between the app’s final read and the write can still race the approval.

## What each action may do

| Action | Default boundary |
| --- | --- |
| Review | Inspect other authors’ code and save private findings; never modify their branches. |
| Author follow-up | Isolate edits, test, commit and push only under its own follow-up permission; verify remote content before completion drafts. |
| Stack follow-up | Prepare a plan and identify the proposed target and changes. |
| Pipeline failure | Check existing reservations and claim unowned work automatically under Trusted and Max; a separate checkpoint can require confirmation. Source pipelines bind to the live source head. Merged-result pipelines bind their immutable commit to the current source and target parents. When only the target is stale, Trusted and Max request one current MR pipeline before any code fix. The account, MR, source, target, old pipeline and exclusive reservation are rechecked; a durable attempt is saved before the request, and an uncertain reply is never blindly retried. Full CI traces stay out of the preparation prompt. Infrastructure job retries still need a listed project and verified current pipeline evidence. |
| Conflict resolution | Prepare a resolution. A push requires its separate toggle, the additional project-task permission and the active scope plus any configured project restriction. |
| Merge | Enabled by Max or by choosing **Auto-merge → On** for your own MR. Requires automatic public-action consent, active scope, required approvals, resolved discussions, an eligible pipeline, merged dependencies, a verified stack target and the checked source SHA. **Default** also applies the configured auto-merge project restriction. |
| To-do events | A recognized event is marked read only after its MR action is durably recorded and the live MR refreshed. This acknowledges the event, not the agent’s work. Unknown events remain unread in Other. Explicitly ignored MR events are acknowledged without running a task. |
| Legacy shell rules | Retained for reference and compatibility. They do not run automatically or get replaced by an AI task. Choose the selected agent CLI in Settings to migrate the handler. |

The Mac toolbar's **Automation** lightning button asks you to confirm pausing or resuming automation app-wide. Pausing cancels running automatic tasks. Resuming can immediately run eligible actions under your saved settings. Select **Don't ask again** and confirm to skip both prompts in the future. Restore confirmations in **Settings → Automation → Advanced**.

The **Automation** lightning button on Mac cards and in Details shows the MR's automation state, its source, rules and holds using cached data. **Default** follows repository, Draft and global settings and displays the resulting action settings. **Off** pauses automation for the MR and displays each action as off. Both modes keep the choices saved under **On**. Select **On** again to restore and edit those choices. The main button and Option-click switch directly between enabled and paused. The **… → Automation** and context menus offer the same choices. The global switch and public action permissions still apply, and pausing keeps the MR on your list. iOS Details shows the MR state and source under Overview.

**Pause automation for Draft MRs**, under Settings → Automation → Scope, defaults to on for new and existing settings. In Default, Drafts are tracked without automatic agent assessment, reviews, publication, fixes, conflict work or CI actions. Factual catalog/dependency reads and recording accepted to-do events are tracking. Turning this preference off or choosing **Automation → On** permits the same configured work as on a Ready MR. Drafts never merge automatically, and headless workers must preserve Draft/Ready status.

Changing a Draft to Ready under Default resumes the configured rules, and changing it back pauses them. Explicit **On** and **Off** persist across Draft and Ready changes. **Mark ready** is a separate manual action for your own open Draft with fresh account, ownership, head and result checks. It can resume configured automation. Manual GitLab actions follow their usual prerequisites.

Saving automation policy or scope changes synchronizes proof permissions immediately. Scope changes cancel only automatic work for targets that are now inactive, preserving unrelated and manually started work. Other automation policy changes cancel active app-owned agent work. Historical script execution remains internally compatible, but is not an available MR automation mode. Remote actions are rechecked at their relevant boundaries; actions already accepted by GitLab cannot be undone by cancellation. Manual actions remain explicitly user initiated.

## What the agent sees

Prepared diff and discussion excerpts filter common credential patterns. Worker tasks can also read files and live GitLab data through their full tool access; these later reads are not covered by the preparation filter. The verifier can also read live evidence through its CLI tools; those reads share the same provider and data-sharing considerations. Scope automation to repositories you may share with the chosen provider. Settings, task history and results are stored on the Mac; task content and data read by the worker can be sent to the CLI’s provider.

## Coordinating pipeline work with another session

A manually started task can reserve an MR before attempting a fix by creating the same local directory atomically. Use the same installation storage root as the running app; the fallback below is the release installation. Replace the host, project ID and MR IID:

```sh
mergetether_storage_root="${MERGETETHER_STORAGE_ROOT:-$HOME/Library/Application Support/com.vaporpw.MergeTether}"
claim="$mergetether_storage_root/Pipeline Work/host-gitlab.example.org/project-123/mr-456/active"
mkdir -p "$(dirname "$claim")"
mkdir "$claim" || exit 1
# Keep the reservation until this task finishes.
rmdir "$claim"
```

Remove only a reservation created by the current task. Trusted and Max check these reservations and claim unowned pipeline work atomically. With the automatic pipeline ownership permission off, unverified ownership requires confirmation. Existing failures are discovered on the first enabled poll and persisted pipeline identities prevent replay across restarts. Interrupted runs can leave a reservation; inspect the associated execution before clearing it. A pipeline-refresh attempt is stored separately before requesting current-target CI, including when the server response is uncertain.


New app-owned reservations record the exact installation, run, reservation token and process session. Startup may recover only a precisely matching known terminal run whose recorded app process is definitively dead; active, interrupted, unknown, reused-PID, foreign or suspicious filesystem entries remain held. Immutable pipeline receipts are retained. Legacy shared reservations and receipts remain read-only negative deduplication checks, never current proof of authority. There is no age-based expiry or automatic deletion of unknown locks.

Before claiming an automatically detected failure, MergeTether can retry a failed read of the initial pipeline evidence. An exhausted read can resume the same workflow entry when GitLab recovers, including after restart. The retry ends before acquiring a reservation or requesting a new pipeline.

### Independent feedback and manual decisions

Treating every unknown as informational would waive real requirements; retaining reviewer-wide blockers would stall unrelated work. A source-bound manual decision separates merge readiness from executable work without waiving either.

Feedback readiness is scoped to the concrete discussion. An unresolved comment, including a closed GitLab thread whose obligation is still demonstrably unmet, remains visible at its own source. It does not transfer its explanation or prevent independently addressed and accepted threads from completing merely because the same reviewer participates in both. Approval, reply, account, head and live-write checks still apply. MR-wide re-review and merge readiness still retain genuinely unresolved concerns.

The semantic verifier compares the original obligation with current code, tests and authoritative requirements. A conditional request to preserve an explicit upstream response can be addressed by verified mapping and a focused stub test; that test does not prove what the real provider emits. A residual provider-contract unknown blocks only when the original concern or an authoritative requirement depends on it. Correcting a prior over-expanded obligation is permitted without inventing a new code change.

After bounded available evidence checks, an essential external decision can remain `uncertain` with a source-bound `manualDecision`: problem context, verified facts (including limits of stubs), missing evidence and sources checked, the precise question, and merge impact. All five fields are required, bounded and validated. Mac and iPhone Details show the full explanation. This is a request for human resolution, not acceptance, an ignore decision or a GitLab write. It cannot authorize automatic resolution or merge. Only this note is excluded from automatic correction work; independent fixes and owed replies continue. Recoverable tool failures and checks the configured assistant can still perform remain ordinary verification work. New code, discussion evidence or an explicit recheck can reassess the decision. The policy version invalidates old cached verdicts while preserving prior note scope.
